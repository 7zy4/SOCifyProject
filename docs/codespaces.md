# تشغيل SOCify في Codespaces

## تشغيل V4 والدخول بأمر واحد

داخل Codespaces أوقف خادم المشروع السابق بـCtrl+C في طرفيته، ثم:

```bash
cd /workspaces/SOCifyProject
git switch V4
git pull --ff-only origin V4
.venv/bin/python run.py --demo --port 5001
```

هذا هو مسار التجربة المعتمد. يجري فحص Docker، ويبني صورة التحليل إذا اختلفت عن
مصدر V4 الحالي. إذا كان مخزن البناء الافتراضي تالفًا (`parent snapshot … does not
exist`)، يستخدم باني Buildx مستقلًا تلقائيًا دون حذف صور أو volumes. يحدّث حاوية
التحليل القديمة بعد التحقق من مسارها، وينفّذ تحقق YARA معزولًا حقيقيًا قبل إنشاء
التجربة، ثم يجهز القضايا والتحليل والتقرير ويختبر دخول الحسابات الأربعة فعليًا.

انتظر `Verified real login for 4 saved demo accounts` ثم `Running on`.
افتح رابط `Login URL` المطبوع، أو **Ports → 5001 → Open in Browser** مع إبقاء
المنفذ Private. اترك طرفية التشغيل مفتوحة.

افتح Terminal ثانيًا ونفّذ هذا الأمر **لفتح الملف في المحرر**:

```bash
code -r instance/v4-codespace-login/accounts.json
```

استخدم `manager@demo.socify.test` وكلمة المرور المقابلة له من حقل `password`
بدون علامتي الاقتباس. لا تكتب مسار JSON وحده في الطرفية؛ الملف بيانات وليس برنامجًا.
ولا تُستخدم كلمات مرور بيئة المساعد أو بريد شخصي لم يُنشأ في هذه التجربة.

| الحساب | الصلاحية |
| --- | --- |
| `manager@demo.socify.test` | مدير الفريق واعتماد القضايا |
| `analyst@demo.socify.test` | محلل مستوى أول |
| `responder@demo.socify.test` | مستجيب مستوى ثانٍ |
| `reviewer@demo.socify.test` | مراجع حسب الصلاحيات المسندة |

تظل التجربة المكتملة وحساباتها ومفاتيحها كما هي عند إعادة الأمر. إذا كانت محاولة
التجهيز القديمة ناقصة، يتحقق السكربت أنها بيانات تجريبية معروفة ويحفظها في مجلد
`v4-codespace-login.incomplete-…`، ثم ينشئ نسخة مكتملة في المسار الأصلي. التجهيز
الجديد يتم في مجلد مرحلي؛ لا يصبح المجلد النهائي متاحًا قبل اكتمال التحليل والتقرير.
تُحفظ المجلدات غير المعروفة دون تغيير ويوقف السكربت العمل. جميع هذه الملفات محلية
وخاصة ولا تنتقل عبر Git. استعادة حساب هذه النسخة عند الحاجة:

```bash
.venv/bin/python -m scripts.recover_v4_demo --directory instance/v4-codespace-login
```

`python run.py` دون `--demo` يظل مسار تشغيل قاعدة التطبيق العادية؛ حسابات التجربة
تخص مسار `--demo`. الغرض من العلم توحيد الخادم وقاعدة الحسابات والمفاتيح.

## V4: إصلاح NO_PUBKEY وتشغيل التجربة

إذا انتهى إنشاء البيئة بـ`docker-in-docker` ورمز `100`، ومعه `NO_PUBKEY 62D54FD4003F6525` و`dl.yarnpkg.com`، فالسبب مصدر Yarn الموروث في صورة التطوير. أصلح V4 ترتيب البناء لإزالة هذا المصدر غير المستخدم قبل تثبيت Docker، مع بقاء فحص توقيعات APT. حاوية Alpine التي تظهر بعد الفشل هي حاوية استرداد وليست بيئة التشغيل المكتملة.

من طرفية **Codespace الموجود نفسه**، حتى لو كانت حاوية استرداد:

```bash
cd /workspaces/SOCifyProject
git fetch origin
git switch V4
git pull --ff-only origin V4
```

ثم افتح Ctrl+Shift+P واختر **Codespaces: Rebuild Container**. انتظر اكتمال البناء وتثبيت الاعتماديات. لا تحذف Codespace أو `instance` أو ملفات المفاتيح. إن منع Git التحديث بسبب تعديلات محلية، احتفظ بها ولا تستخدم reset أو clean.

بعد إعادة البناء، افتح Terminal جديدًا ونفّذ:

```bash
cd /workspaces/SOCifyProject
bash scripts/try_v4_demo.sh
```

الأمر يبني خدمة التحليل ويشغّلها، ثم ينشئ بيانات V4 المعزولة إن لم تكن موجودة، أو يعيد تشغيلها دون تغيير الحسابات وكلمات المرور. افتح `instance/v4-demo/accounts.json` داخل محرر VS Code للحصول على حسابات بيئتك الجديدة؛ كلمات مرور بيئة المساعد السابقة لا تنتقل عبر Git.

افتح **Ports → 5000 → Open in Browser** مع **Visibility: Private**، ثم `/login`. ابدأ بـ`manager@demo.socify.test` وكلمة المرور من الملف. اختر القضية 1 أو القضيتين 1 و2؛ الطلب 3 لاختبار اعتماد المدير. أبقِ الطرفية مفتوحة، وCtrl+C يوقف التطبيق. عند التشغيل التالي استخدم الأمر نفسه.

إذا ظهر أن المنفذ مستخدم، أوقف خادم المشروع السابق من طرفيته أو اختر منفذًا آخر: `SOCIFY_PORT=5001 bash scripts/try_v4_demo.sh`. إذا وجدت تهيئة سابقة غير مكتملة، لا تحذفها: استخدم `bash scripts/try_v4_demo.sh instance/v4-demo-retry`، ثم اقرأ `accounts.json` من المجلد الجديد. تشخيص البيئة بعد إعادة البناء: `docker info` و`.venv/bin/python --version`. فحص الخادم بعد تشغيله من طرفية ثانية: `curl -fsS http://127.0.0.1:5000/health/ready`.

راجع [تشغيل V4](operations-v4.md)، و[خطوات التجربة](v4-demo-walkthrough.md)، و[تفاصيل الإصلاح](qa/v4-codespaces-yarn-repair.md).

إذا نجح بناء صورة التحليل ثم ظهر `Existing development backend differs`، حدّث V4 وأعد أمر التجربة. يستبدل السكربت حاوية تحليل V4 القديمة بالصورة الجديدة عندما تتطابق هوية الحاوية ومسار IPC المتوقع، ويحفظ قاعدة البيانات والمفاتيح والحسابات. لا يلزم إعادة بناء الصورة الناجحة أو حذف Docker volumes. يظل اختلاف مسار IPC سببًا للتوقف والفحص.

## تشغيل V3 السابق

لا تحذف Codespace أو قواعد البيانات أو المفاتيح. استخدم البرنش الموجود `socify-version-3`. يحفظ التحديث الحسابات والفريق والأدلة؛ لا يغيّر `main` أو V2.

## إصلاح البيئة الموجودة والتجربة

1. أوقف الخادم السابق بـCtrl+C في الطرفية التي تشغله، ثم حدّث V3:

   ```bash
   git pull --ff-only origin socify-version-3
   ```

2. من Ctrl+Shift+P اختر **Codespaces: Rebuild Container** داخل Codespace نفسه. يضيف الإعداد الرسمي Docker-in-Docker اللازم لمحرك التحليل المعزول، ويثبت الاعتمادات. إعادة بناء الحاوية تحفظ ملفات المشروع تحت `/workspaces`، ومنها `instance/socify.db` و`instance/codespaces.env`. لا تختَر حذف البيئة، ولا تستخدم أوامر حذف volumes. لا تتوقع أن تثبيت Docker يحدث بمجرد `git pull` دون إعادة البناء.

3. بعد انتهاء البناء، نفذ من مجلد المشروع:

   ```bash
   bash scripts/try_codespace.sh manager@example.test --recover-access
   ```

   هذا هو البريد الذي أثبت فحص حساب المالك وجوده. استبدله فقط إذا كنت تستعمل حسابًا آخر معروفًا بالفعل. تفحص الأداة المنفذ والحساب وDocker، وتبني محرك التحليل عند الحاجة، ثم تعيد تعيين كلمة المرور إلى قيمة عشوائية قوية محفوظة في ملف محلي خاص. يبدأ الموقع فقط بعد نجاح الخطوات. لا تنشئ حسابًا بديلًا ولا تعطل MFA أو CSRF أو حدود المحاولات.

4. ابحث في الطرفية عن **`Recovery file:`** وافتح المسار الذي يليه داخل محرر VS Code. انسخ كلمة المرور من السطر الأول للملف إلى حقل كلمة المرور. الملف بصلاحية `0600` داخل مجلد خاص `0700` بجانب قاعدة البيانات، ومستبعد من Git وسياق بناء Docker. لا ترسل محتواه أو صورته لأحد. ليست هذه كلمة مرور افتراضية أو رمزًا يُرسل بالبريد؛ تتغير عند تكرار الاستعادة. بعد نجاح الدخول احذف هذا الملف الخاص من المحرر؛ حذفه لا يحذف الحساب.

5. افتح **Ports → 5000 → Open in Browser**، واجعل Visibility = **Private**. افتح `/login` من الرابط نفسه وأدخل `manager@example.test` وكلمة المرور من الملف. اترك MFA فارغًا إذا لم يكن مفعّلًا. عند تفعيله يلزم الرمز أو رمز الاسترداد الخاص بك؛ الاستعادة المحلية لا تتجاوزه. حدّث صفحة الدخول بعد إعادة تشغيل الخادم للحصول على نموذج جديد.

عند التشغيل القادم دون تغيير كلمة المرور:

```bash
bash scripts/try_codespace.sh manager@example.test
```

يجهز Dev Container الإعداد عند البدء بواسطة `python -m scripts.start_codespace --check`؛ لا يبدأ خادمًا خفيًا يشغل المنفذ قبل استعادة الحساب. تبقى الطرفية التي تشغل الموقع مفتوحة، ويوقف Ctrl+C خادم التطوير وعامليه. لا تحتاج إعادة إنشاء `.venv` أو توليد مفاتيح عشوائية في كل مرة.

## إذا توقفت إحدى الخطوات

- **`Docker is missing`**: لم يكتمل تطبيق Dev Container الجديد. نفذ إعادة البناء في الخطوة الثانية، ثم تحقق بـ`docker info`. غياب Docker يمنع التحليل والتقارير المعزولة؛ لا تعطل العزل لتجاوز المشكلة.
- **`Port 5000 is already in use`**: أوقف نسخة SOCify السابقة من طرفيتها. لا تشغّل خادمين ولا تقتل خدمة مجهولة. يمكن اختيار منفذ آخر صراحةً بواسطة `SOCIFY_PORT=5001 bash scripts/try_codespace.sh manager@example.test` وفتحه من Ports.
- **الحساب غير موجود**: راجع مسار `Database:` و`SOCIFY_DATABASE` والقاعدة التي أنشأت فيها الحساب. لا تغيّر البريد إلى حساب لم يُنشأ، ولا تستخدم التسجيل العام؛ الانضمام في V3 بدعوة مدير الفريق.
- **تعذر الدخول بعد محاولات متكررة**: حد المحاولات فعال. انتظر 15 دقيقة دون محاولات إضافية ثم افتح نموذجًا جديدًا واستعمل آخر كلمة مرور محفوظة. لا تمسح سجلات الحماية أو تعطل حدود المحاولات.
- **`كلمتا المرور غير متطابقتين؛ لم يتغير الحساب`**: الاستعادة التفاعلية أُلغيت ولم تحفظ كلمة المرور. استخدم خيار `--recover-access` أعلاه لتجاوز خطأ الإدخال المكرر. يبقى `--reset-password` خيارًا تفاعليًا صارمًا لمن يفضله، وتتوقف أداة التشغيل إذا فشل التأكيد.

فحص الحساب منفصلًا دون تغييره:

```bash
python -m scripts.bootstrap_team --email manager@example.test --status
```

إذا كانت لديك `.venv` مهيأة ففعّلها قبل الأوامر المنفصلة. أداة `try_codespace.sh` تختار Python من `.venv` المحلية إذا وجدت، وإلا تستخدم Python المجهز في الحاوية. لا ترسل ملفات المفاتيح أو cookies أو كلمات المرور إلى الدعم.

## الإعداد الأول فقط

في بيئة جديدة لا تحتوي حسابًا، أنشئ المدير مرة واحدة:

```bash
python -m scripts.bootstrap_team --email manager@example.test --name "مدير الفريق" --team "فريق التحقيق"
bash scripts/try_codespace.sh manager@example.test
```

يطلب الأمر الأول كلمة مرور قوية. لا يغيّر حسابًا موجودًا. يدعو المدير أعضاء الفريق بأدوارهم من المنصة. لا تستخدم حسابات الاختبارات أو seed لحل مشكلة الدخول.

## حدود التشغيل والأمان

الأداة الجديدة للتطوير فقط؛ تشغيل الإنتاج يحتاج إعداداته وخدماته المعتمدة. تحتفظ أداة الحساب والخادم بقاعدة البيانات المجهزة ومفاتيح التطوير المحفوظة. إن سبق تصدير مفاتيح عشوائية بالجلسة بدل مفاتيح `instance/codespaces.env`، أوقف الخادم وافتح طرفية جديدة تستخدم الإعداد الأصلي؛ لا تستبدل المفاتيح التي شُفرت بها الأدلة.

لا تحتاج رمز CSRF يدويًا. يطابق التطبيق عنوان Codespaces المحدد وHTTPS من وسيطه المحلي مع بقاء فحص النموذج والمرجع. لا تعطل `SSL_STRICT` أو تضف wildcard للمضيفين. صحة تسجيل الدخول مثبتة بأدلة اصطناعية في [فحص التشغيل والاستعادة](qa/v3-codespaces-startup-2026-10-26.md)؛ تطبيق الإصلاح على Codespace المالك يتطلب الخطوات أعلاه.

للتشخيص المحلي: `curl -fsS http://127.0.0.1:5000/health/ready`. أوامر `python run.py` و`python -m scripts.start_codespace` تبقى مدعومة عند تجهيز البيئة ومحرك التحليل يدويًا؛ الأداة الموحدة تقلل أخطاء ترتيب الخطوات. راجع [تشغيل V3 داخل الشركة](operations-v4.md) للعزل والحدود والنسخ الاحتياطي. لا تستخدم بيانات شركة حقيقية في بيئة تطوير سحابية غير معتمدة.
