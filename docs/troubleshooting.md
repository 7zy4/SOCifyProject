# استكشاف الأعطال

| العرض | الفحص | الحل |
|---|---|---|
| 400 CSRF | رمز التشخيص على الصفحة أو `csrf_rejected` في السجل | استخدم جدول الأسباب أدناه؛ لا تعطل CSRF خارج الاختبارات |
| 401 بعد الدخول | `auth_sessions` ووقت UTC | تحقق من secret ثابت وsession expiry وعدم إلغاء الجلسة |
| `MFA_KEY_MISMATCH` | مفتاح الاعتماد | استعد المفتاح الصحيح أو أعد MFA عبر Admin بمسار مدقق |
| DB locked | عدد workers ومدة transactions | استخدم workers محدودة مع SQLite أو انتقل إلى PostgreSQL |
| Import rejected | `/api/imports/{id}` | صحح UTF-8/format/timezone/line size ثم أعد ملفًا جديدًا |
| HTTP source `not_configured` | allowlist | النتيجة متوقعة؛ لا يوجد اتصال فعلي قبل worker Sandbox |
| ATT&CK technique missing | `GET /api/attack/catalogs` وmetadata count/version | حمّل Bundle STIX الرسمي بإصدار جديد أو فعّل snapshot محفوظًا؛ لا تعِد استخدام اسم إصدار بمحتوى مختلف |
| Playbook awaiting approval | الدور والحالة | Manager فقط يوافق؛ لا تتجاوز البوابة عبر DB |
| Codespace لا يفتح | Ports وlog | اجعل 5000 Private وافحص `/tmp/socify-gunicorn.log` |

## تكرار خطأ CSRF عند تسجيل الدخول في Codespaces

أكد المستخدم أن تشغيل `python run.py` أعاد تسجيل الدخول للعمل. استخدم هذا المسار للتجربة اليدوية بعد إيقاف الخادم السابق؛ راجع `docs/codespaces.md` للفارق بين خادم التطوير ومشغّل Gunicorn. التعليمات أدناه مخصصة لتكرار المشكلة، وليست خطوات مطلوبة إذا أصبح الدخول يعمل.

الرمز مخفي ويُنشأ تلقائيًا؛ لا يحتاج المستخدم إلى كتابته. يظهر سبب الرفض ومعرف الطلب تحت رسالة الخطأ بعد تحديث الفرع. هذه بيانات تشخيص وليست رمز دخول.

| رمز التشخيص | المعنى | الفحص التالي |
|---|---|---|
| `TOKEN_MISSING` | الطلب لا يحتوي رمز النموذج | افتح `/login` من جديد، وتحقق من استخدام النموذج الحالي |
| `SESSION_MISSING` | جلسة المتصفح لا تحتوي رمز النموذج | تحقق من السماح بملفات الارتباط، وافتح Ports في نافذة مستقلة، واستخدم المشغّل الذي يحمل مفاتيح ثابتة لكل العمال |
| `TOKEN_EXPIRED` | تجاوز الرمز مدة الصلاحية | أعد الإرسال من النموذج الجديد |
| `TOKEN_INVALID` | توقيع الرمز غير صالح | تحقق من استخدام مفتاح ثابت وعدم تشغيل خادم قديم؛ لا تحذف المفاتيح المحفوظة |
| `TOKEN_MISMATCH` | الرمز المرسل يخص جلسة مختلفة | افتح نموذجًا جديدًا من عنوان الموقع نفسه |
| `REFERRER_MISSING` | طلب HTTPS لا يتضمن عنوان الصفحة المُرسِلة | تحقق من سياسة المتصفح أو إضافة تحذف Referer، واستخدم نافذة مستقلة |
| `REFERRER_MISMATCH` | عنوان الصفحة المُرسِلة يختلف عن عنوان الخادم | قارن عنوان Ports بعنوان الطلب وإعدادات الوكيل؛ لا توسّع الثقة في ترويسات الوكيل عشوائيًا |
| `VALIDATION_FAILED` | رفض لا يطابق الأسباب المعروفة | احتفظ بمعرف الطلب وراجع إعدادات الخادم وإصدارات الاعتمادات |

`flask_wtf.csrf` و`csrf_rejected` نصان للبحث داخل السجل، وليسا أمرين للتنفيذ. إذا كان `/tmp/socify-gunicorn.log` فارغًا، فقد يكون الخادم شُغّل يدويًا وتظهر رسائله في طرفيته. بعد إيقاف الخادم الحالي بـ Ctrl+C في طرفيته، شغّل:

```bash
git pull --ff-only origin socify-version-2
SOCIFY_HOST=0.0.0.0 python -m scripts.start_codespace 2>&1 | tee /tmp/socify-login-debug.log
```

اترك الطرفية تعمل، وافتح المنفذ 5000 من Ports عبر Open in Browser، ثم جرّب الدخول. عند الفشل، أرسل رمز التشخيص الظاهر على الصفحة ومعرف الطلب، أو ابحث من طرفية ثانية:

```bash
rg 'csrf_rejected' /tmp/socify-login-debug.log
```

يسجل التطبيق سببًا من قائمة ثابتة ومعرف الطلب فقط في هذا السطر؛ لا يسجل كلمة المرور أو قيمة الرمز أو cookies أو عنوان Referer. بقاء الخطأ بعد تحديث الفرع يحتاج إلى هذا الدليل قبل تحديد إصلاح خاص ببيئة المستخدم.
