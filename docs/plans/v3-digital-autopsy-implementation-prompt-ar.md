# البرومت التنفيذي للنسخة الثالثة — SOCify Digital Autopsy

الحالة: مواصفة تنفيذ، وليست شهادة جاهزية أو إعلانًا بتنفيذ هذه المتطلبات.

المنتج: **SOCify Digital Autopsy**، والاسم المعروض للمنتج باللغة الإنجليزية. الوصف العربي: منصة داخلية لتشريح السجلات والتحليل والتحقيق والتوثيق وإنتاج تقارير الحوادث.

الفرع المعتمد: `socify-version-3`، مشتق من `socify-version-2` عند `ebef507`. يبقى `main` وV2 محفوظين. تاريخ المواصفة: 2026-10-24.

قرار المستخدم الصريح: **عزل كامل؛ تحليل محلي واستيراد نتائج VirusTotal يدويًا دون إرسال بيانات للخارج**. يمنع الاستعلام الخارجي حتى باستخدام البصمات فقط.

## 1. الدور والنتيجة المطلوبة

أنت فريق تطوير منتج وأمن تطبيقي وتجربة مستخدم وجودة. حوّل التطبيق الموجود تدريجيًا من منصة تدريب SOC إلى منصة تحقيق رقمي خاصة بفرق الشركة الداخلية. ابدأ بجرد التنفيذ الحالي وفهمه، واستعمل مكوناته القابلة لإعادة الاستخدام؛ لا تبدأ من الصفر ولا تستبدل المشروع بهيكل جديد.

النتيجة المطلوبة رحلة مترابطة: **إنشاء قضية وسببها وهدفها ← إرفاق السجلات والأدلة ← الفرز والتحليل ← التصعيد والتحقيق ← الاستجابة والتحقق ← المراجعة والتوثيق ← التقرير والأرشفة**. لا تتحول المنصة إلى مجموعة شاشات مستقلة أو بديل مزعوم لجميع وظائف SIEM وEDR وSOAR.

نفذ بعد اعتماد هذه المواصفة داخل الفرع الثالث وحده. لا تعدل `main` أو V2، ولا تنشئ فروعًا إضافية أو تحذف فروعًا أو بيانات. احفظ تقدمًا صغيرًا قابلًا للمراجعة في commits واضحة. حاول رفعه إلى الفرع الثالث، وصرّح عند تعذر المصادقة؛ لا تعتبر commit محليًا نسخة مرفوعة إلى GitHub.

## 2. قواعد البحث وREA قبل تعديل الوظائف

1. اقرأ README والهندسة والمخطط والمسارات والصلاحيات والاختبارات والتقارير والهوية الحالية. افحص السلوك الفعلي قبل اقتراح إعادة بناء أي ميزة.
2. أنشئ جردًا: الميزة، ملفها ومسارها، أدلتها الحالية، تبعياتها، قرار الاحتفاظ/التكييف/الإيقاف، مخاطر ترحيل البيانات والاختبارات المتأثرة.
3. راجع مصادر أولية رسمية لمنصات مثل Splunk Enterprise Security وMicrosoft Sentinel وGoogle Security Operations وIBM QRadar وElastic Security وTheHive وCortex XSOAR وWazuh وSecurity Onion وDFIR-IRIS وTimesketch وVelociraptor وMISP. هذه مجموعة مرجعية وليست ترتيبًا سوقيًا موثقًا.
4. استخلص دورة العمل ومفهوم القضية والأدلة والإسناد والتصعيد والتقرير، ثم صمم تنفيذًا مستقلًا مناسبًا للعزل. لا تنسخ واجهة أو كودًا أو محتوى مملوكًا، ولا تدّعِ تطابقًا أو تكاملًا لم تختبره.
5. استخدم REA فعليًا من `https://github.com/7zy4/rea`، مع الرجوع إلى `https://github.com/morluto/rea` عند الحاجة. سجل إصدار الأداة وcommit وأوامر التشغيل وبصمات الأهداف ومعرفات الأدلة والقيود. قراءة README وحدها ليست استخدامًا للأداة.
6. استخدم مصدر الدليل المناسب: تحليل artifact ثابت لبنية JavaScript، ورصد متصفح لصفحة عامة أو نسخة محلية مصرح بها لفهم تدفق واجهتها، واختبارات التطبيق لإثبات صحة SOCify. وثائق المورد وحدها لا تثبت تفاصيل تنفيذه الداخلي.
7. افصل النتائج إلى مشاهدات واستنتاجات ومجهولات. لا تصف صفحة توثيق عامة بأنها تجربة فعلية لمنتج مدفوع، ولا تحوّل صفر أخطاء parsing إلى دليل خلو من الثغرات.
8. احفظ تقرير البحث ومصفوفة المقارنة والأدلة تحت `docs/research/v3/`. إن تعذر الوصول لمصدر، سجل ذلك صراحة واختر مرجعًا بديلًا موثوقًا دون اختلاق نتائج.

## 3. حدود المنتج وإزالة ما لا يخدمه

احتفظ بالقضايا والأدلة والسجلات والاستيراد والتصدير والملاحظات والمهام والفرق والصلاحيات وMFA والتدقيق وMITRE ATT&CK والصيد والرسوم والتقارير، ثم اربطها بالقضية وكيّفها للعمل الداخلي الحقيقي.

أخرج من التجربة التشغيلية: الدروس والمختبرات الهجومية التدريبية والسيناريوهات الاصطناعية والتقييم والاختبارات التعليمية والنقاط والشارات والترتيب ولوحات المدرب وground truth الخاصة بالتدريب. لا تنشئ حسابات أو سجلات تجريبية تلقائيًا في بيئة الشركة. تبقى fixtures الاصطناعية محصورة في الاختبارات المعزولة.

لا يكفي إخفاء رابط التدريب؛ امنع تشغيل الوظائف المتقاعدة عبر API في الوضع التشغيلي. ضع ترحيلًا موثقًا للبيانات القديمة، وأبقِ أرشيفها ونسخها الاحتياطية وتاريخها قابلًا للاسترجاع. لا تحذف جداول `training_*` عشوائيًا؛ بعضها يحمل حاليًا عزل مساحات العمل، وقد يؤدي حذفه إلى تسرب بين الفرق أو كسر المراجع.

حوّل مؤشرات التقييم إلى مؤشرات تشغيلية ذات معنى، مثل جودة اكتمال القضية وأعمار المهام والالتزام بـSLA، دون درجات تعليمية أو ترتيب الموظفين. حافظ على إدارة قواعد الكشف المفيدة داخليًا دون تحويل المشروع إلى جامع طرفيات أو EDR غير مطلوب.

## 4. بنية الواجهة والرحلة الأساسية

- الصفحة الأولى بعد الدخول: قضاياي، قضايا الفريق وفق الصلاحية، البحث، وإنشاء قضية. لا تملأ الجانب الأيمن بجميع أدوات المنصة.
- إنشاء قضية يتطلب ثلاثة مدخلات أساسية: **اسم القضية، سبب فتحها، الهدف المطلوب من التحقيق**. اقترح أسبابًا وقوالب أهداف قابلة للبحث مع خانة تفصيل قصيرة عند الضرورة. ولّد المرجع والوقت والمنشئ ومساحة العمل تلقائيًا.
- احفظ القضية كمسودة ثم افتح مساحة عملها. لا تشترط وجود مالوير أو نتيجة VirusTotal أو سبب جذري لإنشاء القضية.
- اعرض شريطًا علويًا ثابت البنية لمرجع القضية وحالتها وخطورتها ومالكها، وتبويبات سياقية: الملخص، السجلات والأدلة، التحليل والمؤشرات، التحقيق والخط الزمني، الاستجابة وPlaybook، التقرير والنشاط.
- عند كثرة التبويبات، استخدم تجميعًا واضحًا أو قائمة «المزيد» قابلة للوصول. لا تكدس تبويبات متداخلة أو نماذج كاملة داخل الشريط الجانبي.
- يبقى تنقل عام محدود: القضايا، مهامي، مكتبة الإجراءات، وإدارة الفريق/الإعدادات لمن يملك صلاحيتها. المخزون العام المصرح به يظل متاحًا للأدوار المناسبة؛ فتح أداة قضية يتطلب سياق قضية وصلاحية عليها من الخادم.
- اربط كل سجل ودليل ومؤشر وملاحظة ومهمة وتصعيد ونتيجة تحليل وتقرير بالقضية ومساحة العمل. افتح التفاصيل السياقية دون فقد الفلاتر أو موضع المستخدم.
- اسمح بالحفظ الجزئي والمراجعة التدريجية. وضّح الحقول الناقصة عند الانتقال بين المراحل، دون نماذج طويلة تعيق العمل المبكر.

## 5. حالات القضية والحوكمة

الحالات المقترحة: مسودة، فرز أولي، تحليل، مصعّدة، قيد التحقيق، استجابة/احتواء، تحقق، بانتظار مراجعة، مغلقة، مع مسار إلغاء/دمج/إعادة فتح مضبوط. اضبط الانتقالات بصلاحيات وشروط صريحة في الخادم، ودوّن الفاعل والسبب والوقت والإصدار.

افصل حالة القضية عن حالة التنبيه، وأولوية العمل عن خطورة الأثر، ونجاح الهجوم عن صحة التنبيه. لا تفرض مسارًا خطيًا زائفًا على قضية لا تحتاج تصعيدًا أو على استجابة عاجلة موثقة.

طبّق منع تضارب التعديلات بإصدار أو ETag، وطلب سبب لإعادة الفتح والتجاوزات وتغيير الخطورة، وكشف القضايا المكررة/المرتبطة دون إظهار قضايا غير مصرح بها. لا تغلق القضية قبل أدلة الحد الأدنى ونتيجة التحقيق ومراجعة الدور المخول. يمكن اعتماد «غير محسوم» مع سبب ومراجعته، بدل إجبار المحقق على اختراع نتيجة.

## 6. السجلات والاستيراد والتصدير

1. أعد استخدام دعم CSV وJSON وJSONL/NDJSON وSyslog وLinux auth وApache/Nginx وSysmon XML وEVTX الموجود بعد التحقق من كل صيغة. أضف أي صيغة جديدة فقط بمحلل واختبارات وحدود معلنة.
2. ابدأ كل عملية استيراد من القضية أو اربط مجموعة مصرحًا بها إليها. اعرض معاينة، تخمينًا قابلًا للتصحيح للصيغة والترميز والفاصل والمنطقة الزمنية وربط الحقول، ثم أكد الإدخال.
3. احفظ الأصل كبايتات غير معدلة وبصمة SHA-256 ومصدر ومالك جمع ووقت جمع ووقت استيراد وإصدار parser وسجل provenance. خزّن نسخة مطبّعة منفصلة؛ لا تعدل الأصل لإصلاح العرض.
4. اعرض تقدم المهمة وعدد المقبول والمرفوض والمتكرر وأسباب الرفض ومكان السطر، مع إعادة محاولة آمنة دون تكرار البيانات أو مهمة معلقة بلا نهاية.
5. دعم معالجة غير متزامنة ورفع متدفق/مجزأ عند الحاجة، وحدود حجم وعدد سجلات وطول حقل وعمق بنية ومهلة وذاكرة وتزامن قابلة للضبط.
6. لا تعتبر امتداد الملف دليل نوعه. امنع traversal وXXE وCSV formula injection وZIP bombs والأرشيفات المشفرة غير المدعومة. لا تستخرج أرشيفًا إلا بقيود صريحة للمسارات والحجم بعد الفك والعدد والعمق.
7. مستكشف سجلات بفلاتر قابلة للبحث، نطاق زمني، بحث مقيد وآمن، ترقيم صفحات من الخادم، أعمدة قابلة للاختيار، وعرض الأصل والمطبع جنبًا إلى جنب. لا تحمّل كامل البيانات في المتصفح.
8. تصدير الأصل بلا تغيير، والنسخة المطَبّعة إلى CSV وJSON وJSONL، وملخصات التقرير إلى PDF وHTML. ميّز فلاتر التصدير وتنسيقه وترميزه ومنطقته الزمنية وإصداره؛ لا تعد بتصدير صيغة ثنائية لم تُنفذ.
9. وفر حزمة قضية مع manifest وبصمات الملفات وإصدارات التقارير والعلاقات. استيراد الحزمة يتحقق من سلامتها ومخططها وصلاحياتها، ولا يثق في المالك أو الدور الوارد داخلها.
10. وفر نسخة منقحة مع قواعد حجب وسبب وموافق ودليل ما حُجب، دون تعديل الأصل. لا تتيح تصدير غير منقح إلا بصلاحية مستقلة، وسجل كل عملية تنزيل.

## 7. المؤشرات والأصول وتفاصيل الحادث

افصل **Observable** مرصودًا عن **IOC** ثبتت دلالته. يدعم سجل المؤشرات IPv4 وIPv6 وdomain وURL وemail وhostname وfile path وMD5/SHA-1/SHA-256 مع تصنيف الثقة والحالة والمصدر وأول/آخر مشاهدة وانتهاء الصلاحية والوسوم والدليل المرتبط. البصمة ليست ملفًا خبيثًا مثبتًا وحدها.

احفظ القيم الأصلية والموحدة، وأزل التكرار داخل النطاق المصرح، واربط كل مؤشر بالسجلات والأصول والتنبيهات ونتائج التحليل والقضايا المرتبطة. عرض الروابط المشبوهة يكون defanged افتراضيًا، دون معاينة أو DNS lookup أو تحميل صور خارجي تلقائيًا. لا تجعل حفظ URL يؤدي إلى زيارته.

سجل أصولًا متعددة بأدوار قابلة للتغيير: مصدر/مهاجم محتمل، هدف/مدافع، متأثر، وسيط، غير معروف. لا تفترض أن كل عنوان مصدر هو مهاجم مؤكد. لكل أصل: IP/hostname، النوع، نظام التشغيل عند توفره، المالك، أهمية الأصل، الشبكة/البيئة، والمصدر الذي يثبت الوصف.

أنواع الأصول بقوائم محكومة قابلة للبحث: خادم ويب، خادم تطبيق، قاعدة بيانات، حاسوب مستخدم، راوتر، محول، جدار ناري، جهاز أمني، حاوية/عقدة، أصل سحابي داخلي موثق، جهاز آخر/غير معروف. يسمح المدير بتوسيع القاموس دون كسر القضايا السابقة.

التنبيه يحتوي: المرجع، النوع/القاعدة، منتج الكشف، مصدر السجلات، المصدر/الوجهة والمنافذ والبروتوكول عند توفرها، الحالة، الخطورة، الثقة، الأصل المتأثر، وقت وقوع الحدث، وقت الرصد، وقت الاستلام. يرتبط التنبيه بعدة سجلات، والقضية بعدة تنبيهات وأصول.

افصل قرارات: صحيح خبيث، صحيح حميد، إيجابي كاذب، غير محسوم؛ ونتيجة الهجوم: ناجح، فاشل/محجوب، نجاح جزئي، غير معروف. اعرض أسباب القرار وأدلته واعتماده، لا checkbox وحيدًا دون تفسير.

## 8. المسؤوليات والتصعيد والتوقيت

- الأدوار التشغيلية: مسؤول المراقبة عند الرصد، محلل L1 الذي فرز، الشخص الذي صعّد، الشخص الذي استقبل التصعيد، مستجيب L2 قبل التحقيق عند وجوده، المحقق، مالك القضية، المدير/قائد الحادث، ومراجع التقرير. قد يجمع شخص أكثر من وظيفة حسب سياسة الفريق، مع حفظ التاريخ.
- كل تصعيد سجل مستقل: من، إلى، السبب، الأولوية، الوقت، مستوى الانتقال، ملخص الأدلة، وقت الاستلام/الإقرار، القرار والإجراء. دعم رفض تصعيد أو إعادته مع سبب، وتغيير المناوبة والتسليم دون استبدال المالك السابق في السجل التاريخي.
- لا تستخدم دور المحقق بديلًا عن الشخص الذي استجاب بعد L1 وقبل إحالة التحقيق؛ يمثل كل دور ومرحلة بشكل مستقل.
- احسب زمن الإقرار والفرز والتصعيد والاستجابة والاحتواء والإغلاق من أحداث موثقة. حدد تعريف كل مقياس ونقطة بدايته، ولا تعرض مددًا سالبة أو متوسطات من تواريخ ناقصة.
- احفظ UTC مع إزاحة/منطقة المصدر، وأظهر المنطقة المختارة للمستخدم والتقرير. ميز event time وingestion time وanalyst action time، وسجل دقة الوقت وعدم اليقين وانحراف ساعة المصدر.
- يدير المدير SLA حسب الخطورة وساعات العمل وسياسة الإيقاف مع أسباب وموافقات، وتنبيهات داخلية محلية. لا ترسل بريدًا إلى خدمة خارجية؛ أي قناة داخلية تحتاج إعدادًا واختبارًا مستقلين.

## 9. التحليل والتحقيق والخط الزمني

وفر pivot آمنًا من السجل إلى المؤشر والأصل والتنبيه والقضية والخط الزمني. احفظ عمليات البحث المهمة كآثار قابلة للإعادة مع نطاق البيانات والإصدار، ولا تنفذ لغة استعلام أو regex غير محدودة مباشرة من المستخدم.

اجمع أحداثًا آلية وأحداثًا يضيفها المحقق في خط زمني واحد مع الفلاتر والمصدر والبصمة والثقة. ميز الحدث الملاحظ عن فرضية المحقق وعن الإجراء المتخذ، ودعم تصحيح الوصف بإصدارات دون تغيير الدليل الأصلي.

أضف ملاحظات منظمة وفرضيات وأدلة مؤيدة/ناقضة وعلاقات بين الأصول والمؤشرات. الرسم وسيلة اختيارية لفهم العلاقة، وله بديل جدولي قابل للوصول، وليس بديلًا عن الزمن أو التقرير. لا تربط كيانات عبر مساحات غير مصرح بها.

استخدم MITRE ATT&CK محليًا بإصدار واضح: tactic وtechnique وsub-technique، تعليق المحقق، الثقة، والدليل. لا تعتبر اقتراح تطابق آلي دليلًا نهائيًا، ولا ترفع كتالوجًا خارجيًا عند فتح الصفحة.

السبب الجذري يسجل بفئة قابلة للبحث، وعوامل مساهمة، وشرح قصير وأدلة ومراجع وموافق. فئات مقترحة: اعتماد مخترق، ضعف إعداد، استغلال ثغرة موثقة، تصيد/هندسة اجتماعية، صلاحيات زائدة، فجوة مراقبة، سلسلة توريد، غير معلوم. افصل الدخول الأولي عن عوامل التمكين وعن الأثر.

## 10. Playbooks والاستجابة

استخدم مكتبة محلية بقوالب مثل حساب مخترق، تصيد، نشاط مالوير، هجوم تطبيق ويب، اتصال مشبوه، وتسرب بيانات مشتبه به. القالب مجموعة مهام قابلة للتعديل من المدير، بشروط ومدخلات ومسؤولين وموافقات وأدلة إكمال، لا نص تعليمات عام فقط.

للـPlaybook: مسودة، مراجعة، نشر، إيقاف، إصدارات، ومقارنة تغييرات. عند إسناده إلى قضية، أنشئ نسخة مرتبطة بالإصدار؛ تعديل المكتبة لا يغير القضايا القديمة بصمت. ميز تعديل إجراء قضية عن تعديل قالب الفريق.

سجل لكل خطوة من نفذ ومتى وماذا تحقق وما الدليل ونتيجته: مكتمل، فشل، غير منطبق مع سبب، ينتظر موافقة. لا تسمح لمحلل منخفض الصلاحية بتعديل الخطوات الإلزامية أو تجاوز اعتماد المدير.

فرق بين توثيق استجابة قام بها الموظف على نظام آخر، وتنفيذ آلي حقيقي. الوضع الافتراضي **توثيق ومهام محلية فقط**. لا تضف remote shell أو أوامر جدار ناري أو تشغيل ملف مستورد؛ أي تكامل استجابة داخلي لاحق له سياسة وصلاحية وتوقيع وموافقة وعزل ومراقبة واختبارات منفصلة.

بعد الاحتواء والإزالة والتعافي، سجل طريقة التحقق من زوال الأثر والمالك والمسؤول عن المتابعة والمواعيد والدروس المستفادة والإجراءات التصحيحية. لا يساوي إكمال checkbox إثبات نجاح الاحتواء.

## 11. VirusTotal وتحليل المالوير تحت العزل الكامل

**ممنوع:** رفع ملف أو سجل أو IP أو domain أو URL أو hash إلى VirusTotal أو أي محلل أو LLM أو telemetry خارجي. لا استعلامات سمعة تلقائية، ولا fonts/CDN أو error tracking خارجي، ولا fallback سحابي صامت.

استيراد نتائج VirusTotal يكون يدويًا بصيغة JSON موثقة أو تقرير مرفق. تحقق من المخطط والحجم والنوع والبصمة وتاريخ الفحص ومصدر التقرير، واربطه بالعينة الصحيحة والقضية. سجل من استورده ووقت استيراده وبصمته، ووضح أنه **تقرير خارجي مستورد لم يُعاد التحقق منه عبر الشبكة**.

اعرض عدد المحركات والنتائج والوقت والأسماء والاكتشافات وتعارض النتائج، مع التعامل مع نقص الحقول وتغير الإصدارات. لا تختزل صحة الحكم إلى نسبة اكتشاف، ولا تنسب نتيجة بصمة مختلفة إلى العينة الحالية. يسمح بتوثيق «لا توجد عينة» أو «لم يُنفذ تحليل مالوير» بسبب واضح.

العينات تُعامل كمحتوى عدائي: تخزين حجر منفصل خارج web root، أسماء داخلية عشوائية، تشفير وصلاحية تنزيل مستقلة، تحذير واضح، وعدم العرض inline أو المعاينة النشطة أو التنفيذ في خادم التطبيق أو CI.

التحليل المحلي الساكن، عند تنفيذه، يشمل بصمات ونوع ملف وmetadata ومؤشرات قابلة للاستخراج وYARA مع قواعد محلية موثقة الإصدار والترخيص، داخل worker محدود الصلاحيات والذاكرة والوقت وبلا إنترنت. لا تعامل أسماء الملفات أو strings كأوامر. تحليلات الديناميكية اختيارية خلف Sandbox منفصل معزول، وتبقى «غير مهيأة» حتى يثبت تجهيزها؛ لا تثبت Sandbox داخل خادم الويب.

لا تحمل عينة مالوير حقيقية من الإنترنت لإكمال الاختبارات. استخدم fixtures آمنة مثل EICAR أو ملفات اصطناعية غير قابلة للتنفيذ حيث يلائم، دون الادعاء بأنها تغطي جميع تحليلات المالوير.

## 12. الفرق والصلاحيات والتكامل الداخلي

إعادة استخدام إدارة الفريق الحالية وتطويرها لدورة حسابات داخلية: إنشاء المؤسسة/الفريق من المسؤول، دعوات مقيدة، تعيين الأدوار، إيقاف الحساب وسحب الجلسات وتسليم ملكية القضايا. لا تسجيل عام مفتوح افتراضيًا.

أدوار مبدئية: مسؤول المنصة، مدير الفريق، محلل L1، مستجيب L2، محقق، مراجع/مدقق للقراءة، وقارئ تقرير بصلاحية محددة. الصلاحية تعتمد على المؤسسة والفريق وعضوية القضية ونوع العملية؛ مسؤول الإعداد لا يحصل تلقائيًا على قراءة جميع الأدلة الحساسة دون قرار سياسة موثق.

يستطيع المدير إسناد قضية أو مجموعة سجلات/مهمة إلى عضو أو أعضاء مع نطاق وموعد وأولوية، ثم متابعة الاستلام والتقدم والتصعيد. الإسناد داخل القضية لا يمنح الوصول تلقائيًا إلى كامل مخزن سجلات الفريق. أظهر سبب منع الوصول دون كشف بيانات قضية أخرى.

طبق عزلًا من الخادم لكل قائمة وبحث وعدد ورسم وتنزيل وتقرير ونتيجة مهمة. اختبر IDOR وBOLA لكل مورد مترابط، لا للشاشة الرئيسية فقط. كل صلاحية جديدة تدخل قاموسًا مركزيًا وتُغطّى باختبار سماح ورفض.

دعم هوية محلية مع MFA وجلسات ثابتة آمنة. تكامل LDAP/AD/OIDC داخلي قرار توسعة موثق، وليس اعتمادًا مطلوبًا على مزود سحابي. لا تتجاوز سياسات حسابات الشركة أو تربطها تلقائيًا بعنوان بريد غير موثق.

## 13. التقارير المهنية الجاهزة

أنشئ تقريرًا تنفيذيًا مختصرًا وتقريرًا فنيًا مفصلًا من بيانات القضية، مع معاينة وإصدار مسودة ومراجعة واعتماد ونسخة نهائية غير قابلة للتعديل الصامت. أعد توليد إصدار جديد عند تغير البيانات، ولا تستبدل Snapshot معتمدة.

محتوى التقرير حسب الصلاحية:

1. الغلاف، اسم المنتج والشركة، مرجع القضية، تصنيف السرية، المالك، الإصدار، تاريخ الإنشاء والاعتماد.
2. السبب والهدف والنطاق والمنهج والقيود والملخص التنفيذي والنتيجة ومستوى الثقة.
3. الأجهزة المهاجمة/المشتبه بها والمدافعة والمتأثرة، الأنواع والمالكون والأثر.
4. مصادر السجلات وطرق جمعها والمحللات وبصمات الأدلة ومراجع provenance.
5. تفاصيل التنبيهات وحالتها وخطورتها وقرار صحتها، ونتيجة الهجوم منفصلة.
6. المؤشرات والأدلة وخط زمني واضح بتواريخ ومناطق زمنية ومراجع قابلة للتتبع.
7. ربط MITRE ATT&CK بإصداره وأسباب الربط، ونتائج البحث والتحليل والفرضيات.
8. المسؤوليات وسلسلة التصعيد واستلام كل مرحلة وأزمنة الإقرار والاستجابة والاحتواء.
9. Playbook وإصداره والخطوات ونتائج التنفيذ والموافقات والاستثناءات.
10. السبب الجذري والعوامل المساهمة والتحقق من الأثر والاستجابة والتعافي والتوصيات والمالكين والمواعيد.
11. نتائج المالوير وVirusTotal المستوردة عند وجودها مع مصدرها وحدودها، أو سبب عدم انطباقها.
12. سجل المراجعة والاعتماد وفهرس الأدلة والملاحق، وما بقي غير محسوم أو خارج النطاق.

لا تطبع حقولًا وهمية ولا استنتاجات آلية غير مدعومة. ميز «غير متوفر» و«غير منطبق» و«لم يُختبر» عن الفراغ. اسمح بمقاطع سردية قصيرة للمحقق؛ استخرج الباقي تلقائيًا من الحقول والعلاقات.

PDF وHTML يجب أن يعملَا دون شبكة أو أصول خارجية، مع تضمين الخطوط/الأصول محليًا. لا تسمح لمحرك PDF بقراءة مسارات الخادم أو زيارة URLs وردت في الأدلة. اختبر RTL وLTR وفواصل الصفحات والجداول الطويلة ونصوصًا عربية/إنجليزية مختلطة وبصمات طويلة.

## 14. تقليل الكتابة والتحقق من كل مدخل

ابدأ بقيم تلقائية موثوقة من السجلات والدليل والحساب، ثم قوائم قابلة للبحث ومراجع كيان قائمة، ثم نص حر حيث يتطلب التحقيق شرحًا. اجعل الأصول والأعضاء والمصادر وأنواع التنبيه والحالات والخطورة والأسباب الجذرية وATT&CK والقوالب قوائم منظمة.

وفر «أخرى» بتفصيل قصير عند الحاجة، وقاموسًا قابلًا للإدارة مع صلاحية وتاريخ. لا تستبدل النصوص الحرة الضرورية بقائمة تمنع تسجيل واقعة غير مألوفة، ولا تجعل القوائم تفتح مئات آلاف الخيارات دفعة واحدة.

لكل حقل عقد يحدد النوع والطول والترميز والقيم المسموحة والمطلوب والتبعيات ونطاق الصلاحية. تحقق في الخادم قبل الاستخدام، ثم تحقق واجهي مساعد. ارفض الحقول غير المعروفة وmass assignment ولا تثق في hidden inputs أو dropdown IDs.

تحقق من IP وdomain وURL وhash والطوابع الزمنية والأرقام وأسماء الملفات والمراجع على نحو مخصص. استخدم استعلامات SQL ذات معاملات، وترميز إخراج حسب السياق، ونصًا آمنًا للملاحظات أو Markdown مقيدًا بلا HTML نشط. افصل تطبيع البحث عن بايتات الدليل.

عالج Unicode والتحكم في اتجاه النص والأحرف غير المرئية في العرض الأمني دون إفساد الدليل الأصلي. امنع log injection وheader injection وCRLF، واعرض الأخطاء قرب الحقول برسائل مفهومة ومعرف ارتباط آمن؛ لا تطلب من المستخدم إدخال CSRF يدويًا.

الألوان المرجعية: الأزرق `#1C4286`، البرتقالي الأحمر `#DD4027`، لهجة الشارات `#CB3B24`، الذهبي `#F3A257`، الأزرق الباهت `#E4ECF8`، الأبيض `#FFFFFF`، العاجي `#FBF7F0`، محيط الورق `#C9D1DE`، النص `#1D3461`، الخافت `#4A5A7A`، الفواصل `#B9C8E4`.

التزم بلوحة مفاتيح وfocus واضح وتسميات مترابطة وcombobox قابل للوصول ورسائل قارئ الشاشة وWCAG 2.2 AA في الرحلات الأساسية. اختبارات axe مهمة لكنها لا تغني عن اختبار لوحة المفاتيح والمراجعة البصرية.

الطباعة A4 وهوامش وتضمين خطوط وفق دليل الهوية، مع رأس جدول متكرر وصفحات إضافية عند الحاجة، وعدم قص الأدلة أو تصغيرها قسرًا. سلّم دليل هوية V3 مستقلًا بصيغتي HTML وPDF مع أمثلة الموقع والتقرير.

## 16. نموذج البيانات والترحيل والجودة

ابدأ من المخطط الحالي. أضف/كيّف كيانات مؤسسة/فريق وعضوية قضية، case purpose/objective، أصل، observable/IOC، ربط تنبيه/سجل، مسؤولية زمنية، تصعيد، إجراء استجابة، نسخة Playbook، تشغيل/تقرير تحليل، نتيجة سمعة مستوردة، ومراجعة تقرير. ضع قيودًا وفهارس وعلاقات وإصدارات وسياسة حذف لكل كيان، ولا تكدس كل شيء في JSON حر غير مقيد.

اكتب migrations بإصدارات قابلة للتطبيق على نسخة V2 واقعية، مع نسخة احتياطية وخطة تراجع واستعادة مجرّبة. قارن عدد السجلات والعلاقات وبصمات الأدلة والتقارير قبل/بعد. حافظ على مفاتيح التشفير السابقة ولا تولد بديلًا عنها بصمت.

لا تكسر روابط التقارير والأدلة التاريخية أو تعيد نسب منشئها. وثق توافق API وإهمال المسارات التدريبية، وحدّث OpenAPI. افصل منطق المجال والتحقق والصلاحيات عن handlers وعرض الواجهة دون إعادة هيكلة شاملة غير لازمة.

اعتمد وظائف صغيرة بأسماء واضحة، وأنواعًا وعقودًا متسقة، وأخطاء موحدة، وفحوص lint/type. لا تضف تعليقات تعليمية أو تعليمات تشغيل داخل الكود؛ وثق القرارات في الملفات المناسبة، واحتفظ بتعليقات الترخيص أو الاستثناء الأمني الملزمة فقط.

## 17. Secure SDLC والعزل والتوسع

حدد threat model يشمل موظفًا محدود الصلاحية، حسابًا مخترقًا، مستندات/سجلات/عينات عدائية، محلل ملفات معيبًا، مديرًا يسيء الاستخدام، وتصديرًا غير مصرح. اربط المخاطر بضوابط واختبارات فعلية.

افرض مصادقة وصلاحيات افتراضيها المنع، MFA وسياسة جلسات، rate limits، CSRF وحماية XSS وSSRF وXXE وpath traversal وcommand injection وdeserialization وSQL injection، وقيود تحميل وتنزيل وتصدير. لا تعطل أي اختبار أو قاعدة حماية لتجتاز البوابات.

إخراج الشبكة محظور افتراضيًا على التطبيق وworkers ومحرك التقارير والتحليل. اختبر على مستوى البيئة/الحاوية، فغياب طلبات fetch في كود واحد لا يثبت العزل. اسمح فقط باتصالات الشركة الموثقة المطلوبة كقاعدة بيانات داخلية أو IdP محلي؛ دون إنترنت أو cloud fallback أو DNS خارجي ضمن التحليل.

لا LLM خارجي أو telemetry أو crash reporting خارجي. أي مساعد محلي مستقبلًا يجب أن يعامل السجلات كبيانات غير موثوقة، ويمنع prompt injection من تشغيل أدوات أو تغيير صلاحيات أو إرسال أدلة، ويستند إلى أدلة مع مراجعة بشرية. ليس المساعد الذكي شرطًا للنسخة الأولى التشغيلية.

احفظ الأسرار في آلية داخلية مع صلاحيات وتدوير ونسخ احتياطي، دون طباعة قيمها أو إدراجها في Git. استخدم تشفيرًا معتمدًا للنقل والتخزين حسب بيئة الشركة ولا تخترع cryptography خاصة.

العامل الذي يحلل الملفات محدود الصلاحيات، مع مسار بيانات وحجر واضح، وحدود موارد وعزل منفصل عن الويب. حالات المهام queued/running/succeeded/failed/cancelled مع idempotency وإعادة محاولة محدودة واستعادة بعد انقطاع العامل ومراقبة صحة.

سجل تدقيق مترابطًا للأحداث الحساسة يتجنب الأسرار ومحتوى السجلات الخام، ويحمي من العبث وفق نموذج التهديد. لا تزعم أن قيد منع تعديل داخل SQLite يمنع مسؤول نظام لديه وصول كامل من العبث. اختبر النسخ والاستعادة والاحتفاظ وlegal hold وحذفًا مصرحًا بعد انتهاء السياسة.

ابدأ بقياس SQLite الحالي تحت حمل ممثل؛ لا تستبدله دون حاجة. جهّز حدودًا واضحة للتوسع عبر workers منفصلين وفهارس وبحث مُرقم وتخزين كائنات داخلي وPostgreSQL عند إثبات الحاجة. لا تدّعِ توافق PostgreSQL قبل migrations واختبارات فعلية.

ضع ملف أداء قابلًا للإعادة يحدد حجم السجلات والأدلة وعدد المستخدمين المتزامنين ومواصفات البيئة وحجم الدفعة. قِس p50/p95/p99 للاستيراد والبحث وفتح القضية والتقرير، وذاكرة/CPU، ثم اتفق على SLO. إن تعذر تحديد حمل الشركة، ابدأ بمرجع اصطناعي مليون سجل و20 مستخدمًا متزامنًا بوصفه هدف اختبار مقترحًا، لا قدرة مثبتة. لا تستخرج رقم تحمل من اختبار بيانات صغيرة.

## 19. مراحل التنفيذ والحفظ عند الانقطاع

1. **البحث والتأسيس:** هذه المواصفة، جرد V2، مقارنة المصادر، أدلة REA، threat model، نموذج البيانات وخطة الترحيل، ومصفوفة المتطلبات. لا تضع علامة تنفيذ على مجرد مستند.
2. **الرحلة المركزية:** هوية المنتج، إنشاء القضية، التنقل السياقي، فصل وظائف التدريب، وإسناد الفريق؛ اختبر دون كسر القضايا الموجودة.
3. **الأدلة والتحليل:** الاستيراد والربط والمؤشرات والأصول والتنبيهات والخط الزمني وATT&CK، مع عزل وصلاحيات كل مورد.
4. **سير العمل:** المسؤوليات والتصعيد وSLA وPlaybooks والتحقيق والاستجابة، ثم التحليل المحلي واستيراد تقارير الفحص.
5. **التوثيق والتسليم:** التقارير والهوية V3 والترحيل والنسخ والاستعادة، ثم اختبارات الأمن/الأداء/المتصفح والمراجعة النهائية.

بعد كل وحدة متحققة: commit وصفي، محاولة push للفرع الثالث، تحديث سجل التقدم بمعرف commit والأوامر والنتائج والقيود والخطوة التالية. عند فشل الرفع، أنشئ patch أو Git bundle خارجيًا للاستكمال، ولا تضع أسرارًا أو بيانات شركة في الأدلة أو اللقطات.

نفذ فحوص الجودة والنوع والاختبارات المناسبة والتغطية وفحص الاعتمادات والأسرار وSAST، وراجع الثغرات الحرجة/العالية وأصلحها قبل إعلان الجاهزية. لا تعالج فشل الاختبارات بحذفها أو تعطيلها أو تخفيف assertions أو استثناءات أمنية واسعة.

## 20. شروط التسليم والصدق في النتيجة

المخرجات المطلوبة: التطبيق المكيّف، migrations، عقود API، دليل تشغيل داخلي/عزل، دليل محلل ومدير، دليل هوية V3 مستقل، قوالب تقارير، مقارنة المنصات، أدلة REA، مصفوفة المتطلبات والرحلات، نتائج الاختبارات، وملف بالمشكلات المتبقية وخطة استكمال قابلة للتنفيذ.

لا تعلن «نسخة نهائية» أو «متوافقة 100%» أو «بلا ثغرات» اعتمادًا على التشابه البصري أو نجاح مجموعة اختبارات محدودة. يجوز إعلان الجاهزية فقط للمتطلبات التي لها دليل قبول، مع بيئة وإصدار ونطاق معروف، وصفر عوائق قبول معلنة، ومراجعة أمنية ومراجعة بصرية فعلية.

إذا كانت النتيجة جزئية، اذكر ما نُفذ وما ثبت وما بقي وماذا يمنع التحقق. لا تخفِ نقص التكامل أو عزلًا غير مختبر خلف اسم زر. اطلب من المالك قرارًا فقط عندما يمنع غموض جوهري التقدم؛ تقدم في الأعمال المستقلة وفق الافتراضات المدونة، ولا تكرر السؤال عن قرار سبق حسمه.
