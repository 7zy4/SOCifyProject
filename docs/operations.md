## Docker Compose

1. جهّز قيمتين مستقلتين وقويتين لـ`SOCIFY_SECRET_KEY` و`SOCIFY_CREDENTIAL_KEY`: في ملف `.env` بجانب `docker-compose.yml` (أوامر إنشائه في [التشغيل](../README.md#التشغيل))، أو من مدير الأسرار في بيئة المؤسسة.
2. تأكد من حفظ المفاتيح لاستعادة الأدلة؛ لا تعتمد على قيم مؤقتة تتغير مع إعادة التشغيل.
3. ابنِ الخدمات وشغّلها، ثم أنشئ حساب المدير داخل خدمة التطبيق:

```bash
docker compose up -d --build
docker compose exec socify python -m scripts.bootstrap_team --email owner@example.com --name "مالك المنصة" --team "فريق العمليات"
curl -fsS http://127.0.0.1:5000/health/ready
```

4. افتح <http://127.0.0.1:5000>. للنشر الخارجي، اضبط TLS والمضيف الفعلي كما هو موضح أدناه.
5. لعرض القاعدة المستخدمة وحالة الحساب دون تعديل أي شيء:

```bash
docker compose exec socify python -m scripts.bootstrap_team --email owner@example.com --status
```

| الخدمة | وظيفتها | الوصول |
|---|---|---|
| ingress | مدخل NGINX | ينشر المنفذ على loopback فقط؛ بلا قاعدة أو مفاتيح |
| socify | الواجهة وAPI عبر Gunicorn | شبكة داخلية وقاعدة ومقبس التحليل |
| import-worker | معالجة الاستيرادات | بلا شبكة؛ قاعدة ومفاتيح فك أدلة الرفع |
| autopsy-worker | التحليل والتقارير | بلا شبكة؛ قاعدة ومقبس التحليل |
| analysis | الفحص الساكن وإخراج المستندات | بلا شبكة أو قاعدة أو مفاتيح التطبيق |
| backup | نسخ احتياطي مجدول للقاعدة | بلا شبكة ولا مفتاح اعتماد؛ حجم البيانات وحجم `socify-backups` |
| egress | الإرسال الخارجي (Webhooks والبريد) ووسيط الطلبات المتزامنة | معطّل افتراضيًا (ملف Compose `egress`)؛ الخدمة الوحيدة المتصلة بالإنترنت، بلا قاعدة القضايا ولا مفتاح الاعتماد ولا مقبس التحليل؛ حجم `socify-outbox` فقط |

- تخزن البيانات في حجم `socify-data`؛ يتبادل التطبيق والتحليل الطلبات عبر `analysis-ipc`.
- لكل خدمة فحص صحة يظهر في `docker compose ps`: التطبيق والمدخل يفحصان `/health/ready`، والعاملان وخدمة النسخ يقرؤون نبضهم من القاعدة (`python -m scripts.healthcheck worker --name <الاسم> --max-age 120`)، وخدمة التحليل تُسأل بطلب `ping` لا ينفذ عملًا (`python -m scripts.healthcheck analysis`). كل 30 ثانية، بمهلة 5 ثوانٍ وثلاث محاولات. لا يبدأ التطبيق قبل أن تصبح خدمة التحليل سليمة.
- اضبط وكيل الشركة لإنهاء TLS، ومرّر `SOCIFY_HTTPS=1` و`SOCIFY_TRUSTED_HOSTS` الصحيحين إلى خدمة التطبيق.
- Compose المرفق يستخدم HTTP على loopback. لا تعرضه مباشرة كإعداد TLS مكتمل.
- التطبيق على شبكة داخلية لا تملك خروجًا افتراضيًا؛ سحب مصادر HTTPS يحتاج مسار خروج مصرحًا. دفع السجلات إلى موصل القضية لا يتطلب خروج التطبيق.
- لا تستخدم `docker compose down -v` للإيقاف المعتاد؛ الخيار يحذف أحجام البيانات.
- لإيقاف الخدمات مع الاحتفاظ بالبيانات: `docker compose down`.

## الإعدادات الأساسية

| المتغير | الغرض |
|---|---|
| `SOCIFY_ENV=production` | إعداد الإنتاج، مع مفاتيح صريحة وعمال منفصلة |
| `SOCIFY_DATABASE` | مسار قاعدة البيانات المشتركة بين التطبيق والعمال |
| `SOCIFY_SECRET_KEY` | توقيع الجلسات والحماية المرتبطة بها |
| `SOCIFY_CREDENTIAL_KEY` | تشفير بيانات الاعتماد والأدلة |
| `SOCIFY_CREDENTIAL_KEY_PREVIOUS` | المفتاح السابق أثناء تدوير مفتاح التشفير فقط؛ يُقرأ به ولا يُكتب |
| `SOCIFY_METRICS_TOKEN` | رمز جمع `/health/metrics`، 32 محرفًا على الأقل (مثل `python -c "import secrets; print(secrets.token_urlsafe(32))"`)؛ بدونه يبقى المسار معطّلًا، ورمز أقصر يمنع الإقلاع |
| `SOCIFY_HTTPS` و`SOCIFY_TRUSTED_HOSTS` | HTTPS والمضيفون المسموحون |
| `SOCIFY_TRUSTED_PROXIES` | عدد الوكلاء الموثوقين أمام التطبيق لقراءة عنوان العميل من `X-Forwarded-For`؛ الافتراضي 0، وCompose يضبطه 1 |
| `SOCIFY_SESSION_SECONDS` | العمر الأقصى للجلسة مهما كان النشاط؛ الافتراضي 28800 ثانية (8 ساعات) |
| `SOCIFY_SESSION_IDLE_SECONDS` | تنتهي الجلسة بعد هذه المدة دون طلب من المستخدم؛ الافتراضي 3600 ثانية، و0 يعطّل الحد، وأي قيمة أخرى أقل من 300 تمنع الإقلاع. متابعة حالة المهام في الخلفية لا تمدد الجلسة، وتنبّه الواجهة قبل الانتهاء بدقيقتين |
| `SOCIFY_LOGIN_ATTEMPTS` و`SOCIFY_LOGIN_IP_ATTEMPTS` | حد المحاولات الفاشلة للحساب من عنوان واحد، ثم للعنوان عبر كل الحسابات، خلال `SOCIFY_LOGIN_WINDOW_SECONDS` (الافتراضي 900 ثانية)؛ الافتراضي 5 و50. حد الحساب يعدّ الأخطاء بعد آخر دخول ناجح من العنوان نفسه فقط، وخطوة طلب رمز MFA بعد كلمة مرور صحيحة لا تُعد محاولة فاشلة. حد العنوان لا يصفّره دخول ناجح |
| `SOCIFY_LOGIN_ACCOUNT_ATTEMPTS` | حد أخطاء الحساب عبر كل العناوين بعد آخر دخول ناجح، خلال نافذة الدخول؛ الافتراضي 20، و0 يعطّله. بعد بلوغه لا يُرفض الحساب نهائيًا بل يُبطأ: `429 LOGIN_RATE_LIMITED` مع `Retry-After` يبدأ بـ30 ثانية ويتضاعف مع كل خطأ جديد حتى طول النافذة. العنوان الذي دخل منه صاحب الحساب سابقًا لا يُبطأ |
| `SOCIFY_REAUTH_ATTEMPTS` | حد التحقق الخاطئ من كلمة المرور داخل الجلسة (تغيير كلمة المرور وبدء MFA وإلغاؤه) للحساب عبر كل العناوين خلال نافذة الدخول؛ الافتراضي 5، و0 يعطّل الحد |
| `SOCIFY_REAUTH_REVOKE_SESSION` | عند بلوغ حد إعادة التحقق تُنهى الجلسة الحالية؛ الافتراضي 1، و0 يبقي الجلسة ويرفض المحاولات حتى انتهاء النافذة |
| `SOCIFY_REGISTER_ATTEMPTS` و`SOCIFY_SOURCE_KEY_ATTEMPTS` | حد محاولات التسجيل المرفوضة ومفاتيح المصادر الخاطئة من عنوان واحد؛ الافتراضي 20 |
| `SOCIFY_ANALYSIS_SOCKET` | مسار مقبس خدمة التحليل |
| `SOCIFY_EGRESS_ENABLED` | للتطبيق: يسمح بوضع الرسائل في صندوق الإرسال؛ الافتراضي 0 فلا يُرسل شيء خارج المنصة |
| `SOCIFY_OUTBOX_DATABASE` | قاعدة صندوق الإرسال المشتركة بين التطبيق وخدمة `egress`؛ في Compose `/outbox/outbox.db` على حجم `socify-outbox` |
| `SOCIFY_EGRESS_ALLOWLIST` | لخدمة `egress`: أسماء المضيفين المسموح الاتصال بها، مفصولة بفواصل؛ فارغ افتراضيًا فلا اتصال بأي مضيف |
| `SOCIFY_EGRESS_WEBHOOKS` | لخدمة `egress`: وجهات Webhook بصيغة `name=https://...` مفصولة بفواصل؛ الرسالة تحمل الاسم فقط. السر اختياري في `SOCIFY_EGRESS_WEBHOOK_SECRET_<NAME>` ويوقّع الطلب بـ`X-SOCify-Signature` |
| `SOCIFY_EGRESS_MAX_ATTEMPTS` | لخدمة `egress`: عدد محاولات التسليم قبل اعتبار الرسالة فاشلة؛ الافتراضي 8، والانتظار بين المحاولات يبدأ بـ30 ثانية ويتضاعف حتى ساعة |
| `SOCIFY_SMTP_HOST` و`SOCIFY_SMTP_PORT` و`SOCIFY_SMTP_TLS` و`SOCIFY_SMTP_USERNAME` و`SOCIFY_SMTP_PASSWORD` و`SOCIFY_SMTP_FROM` | لخدمة `egress`: خادم البريد. TLS إلزامي (`starttls` افتراضيًا على 587، أو `ssl` على 465) مع التحقق من الشهادة، والمضيف يجب أن يكون في قائمة السماح |
| `SOCIFY_EGRESS_TOKEN` | لخدمة `egress`: رمز الوسيط الداخلي `POST /relay` على المنفذ 8081 (32 محرفًا على الأقل)؛ غير مضبوط افتراضيًا فالوسيط معطّل |
| `SOCIFY_INTAKE_GROUP_SECONDS` | نافذة تجميع التنبيه الوارد المتكرر بالثواني؛ الافتراضي 3600، والمسموح من 0 إلى 86400 |
| `SOCIFY_BACKUP_INTERVAL_HOURS` | لخدمة `backup`: الفاصل بين النسخ المجدولة بالساعات؛ الافتراضي 24، والمسموح من 1 إلى 720 |
| `SOCIFY_BACKUP_KEEP` | لخدمة `backup`: عدد النسخ الأحدث التي تبقى؛ الافتراضي 14، والمسموح من 1 إلى 1000 |
| `SOCIFY_BACKUP_KEY` | لخدمة `backup` ولـ`scripts.restore --decrypt`: مفتاح تشفير النسخ، 32 محرفًا على الأقل، منفصل عن `SOCIFY_CREDENTIAL_KEY`. غير مضبوط افتراضيًا فتُحفظ النسخ دون تشفير؛ اضبطه في `.env` لتشفيرها |
| `SOCIFY_BACKUP_DIR` | لخدمة `backup`: مجلد النسخ؛ الافتراضي `/backups` (حجم `socify-backups`) |
| `SOCIFY_SOURCE_ALLOWLIST` | أسماء مصادر HTTPS المصرح بها |
| `SOCIFY_MAX_UPLOAD_BYTES` و`SOCIFY_MAX_IMPORT_ROWS` | حدود الرفع والصفوف؛ الافتراضي 10 MiB و100000 صف |
| `SOCIFY_MAX_PENDING_IMPORT_JOBS` | حد طابور الاستيراد؛ الافتراضي 100 مهمة منتظرة |
| `SOCIFY_REQUIRE_CASE_APPROVAL=1` | سياسة اختيارية، معطّلة افتراضيًا: تبدأ القضية الجديدة بانتظار اعتماد المدير، وتبقى أدواتها مقفلة حتى يعتمدها |
| `SOCIFY_REQUIRE_INVESTIGATION_SELECTION=1` | سياسة اختيارية، معطّلة افتراضيًا: لا تُفتح أدوات القضية إلا بعد اختيارها من صفحة القضايا |

## استقبال التنبيهات من SIEM وEDR

- يضيف مدير الفريق التكامل من صفحة الفريق: النوع والاسم والمصادقة (توقيع HMAC أو رمز API) وقاعدة الإنشاء التلقائي. يظهر عنوان الاستقبال، وسر التوقيع مرة واحدة.
- الحدود: 1 MiB للطلب، و100 تنبيه للدفعة، والرد `202` بأرقام التنبيهات وحالة كل منها (`created` أو `grouped`). التوقيع الخاطئ يُعدّ بحد `SOCIFY_SOURCE_KEY_ATTEMPTS`.
- التوقيع: `X-SOCify-Timestamp` بثواني Unix (خلال 5 دقائق)، و`X-SOCify-Signature: sha256=<hex>` لـHMAC-SHA256 بالسر على `<timestamp>.<body>`. الطلب الموقّع نفسه يُرفض إن تكرر (`409`).
- المنصة تستقبل ولا تتصل: يجب أن يصل نظام المراقبة إلى عنوان SOCify عبر الوكيل.

Wazuh (تكامل مخصص في `ossec.conf` على المدير، بمصادقة رمز API):

```xml
<integration>
  <name>custom-socify</name>
  <hook_url>https://socify.example.com/api/intake/1/alerts</hook_url>
  <api_key>socify_pat_...</api_key>
  <level>7</level>
  <alert_format>json</alert_format>
</integration>
```

```bash
#!/bin/sh
# /var/ossec/integrations/custom-socify: integratord passes the alert file, api_key and hook_url.
curl -sS -X POST -H "Authorization: Bearer $2" -H "Content-Type: application/json" --data @"$1" "$3"
```

Elastic Security (موصل Webhook في Kibana: الطريقة POST، والعنوان عنوان الاستقبال، وترويسة `Authorization: Bearer <رمز API>`)، ونص إجراء القاعدة:

```json
{"alerts": {{#toJson}}context.alerts{{/toJson}}}
```

Microsoft Sentinel (Logic App يبدأ بمشغّل التنبيه، ثم إجراء HTTP): الطريقة POST، والعنوان عنوان الاستقبال، وترويسة `Authorization: Bearer <رمز API>`، والجسم كائن التنبيه `@{triggerBody()}`.

Splunk: إجراء Webhook المدمج لا يضيف ترويسات؛ استخدم إجراء تنبيه مخصصًا أو سكربتًا يرسل الجسم `{"sid", "search_name", "result": {...}}` بترويسة `Authorization: Bearer <رمز API>`، أو بتوقيع HMAC.

الصيغة العامة بتوقيع HMAC:

```bash
body='{"alerts":[{"id":"edr-1","title":"Blocked ransomware","severity":"critical","time":"2026-11-26T08:00:00Z","entities":{"hosts":["FS-02"]}}]}'
ts=$(date +%s)
sig=$(printf '%s.%s' "$ts" "$body" | openssl dgst -sha256 -hmac "$SOCIFY_INTAKE_SECRET" -hex | sed 's/^.* //')
curl -sS -X POST "https://socify.example.com/api/intake/2/alerts" -H "Content-Type: application/json" \
  -H "X-SOCify-Timestamp: $ts" -H "X-SOCify-Signature: sha256=$sig" --data "$body"
```

## الإرسال الخارجي

التطبيق والعمال بلا خروج إلى الإنترنت. كل ما يخرج يمر بصندوق إرسال في قاعدة SQLite مستقلة، وتسلّمه خدمة `egress`:

```text
socify / العمال  --(socify-outbox: outbox_messages)-->  egress  --HTTPS/SMTP عبر قائمة السماح-->  الوجهة
      (شبكة داخلية بلا خروج)                          (socify-internal + egress)
```

- الإرسال معطّل افتراضيًا. لتفعيله: اضبط في `.env` قائمة السماح `SOCIFY_EGRESS_ALLOWLIST` والوجهات `SOCIFY_EGRESS_WEBHOOKS` أو إعدادات `SOCIFY_SMTP_*`، ثم `SOCIFY_EGRESS_ENABLED=1`، وشغّل `docker compose --profile egress up -d`.
- الرسالة تحمل اسم الوجهة أو عنوان البريد والمحتوى فقط؛ عناوين Webhook وأسرارها وبيانات SMTP في بيئة خدمة `egress` وحدها.
- كل طلب HTTPS يمر بالعميل نفسه المستخدم لسحب المصادر: مضيف من قائمة السماح وعناوين DNS عامة فقط، واتصال مثبت على العنوان المفحوص، وتحقق TLS، ورفض إعادة التوجيه، ومهلة واحدة وحد لحجم الرد. البريد يتصل بالعنوان المفحوص نفسه مع TLS يتحقق من اسم الخادم.
- الفشل المؤقت (انقطاع، مهلة، 5xx، 408، 429) يُعاد بانتظار متزايد حتى `SOCIFY_EGRESS_MAX_ATTEMPTS`؛ الوجهة غير المعروفة أو رد 4xx آخر يُعد فشلًا نهائيًا. يرى المدير الرسائل وحالتها في `GET /api/outbox` ويعيد إرسال الفاشلة بـ`POST /api/outbox/<id>/retry`.
- للحاجات المتزامنة (مثل الدخول الموحد لاحقًا) يوفر الوسيط `POST /relay` على الشبكة الداخلية، بمصادقة `SOCIFY_EGRESS_TOKEN`، ونوعين فقط من الطلبات: `get_json` و`post_form` إلى مضيفات قائمة السماح.
- خدمة `egress` تكتب نبضها في قاعدة صندوق الإرسال، ويقرؤه فحص الصحة بـ`--database /outbox/outbox.db`.

## العمال المستقلون

- Compose يشغّل العمال؛ الأوامر التالية لمسؤول ينشر الخدمات منفردة.
- استخدم قاعدة البيانات ومفاتيح التشفير نفسها في التطبيق والعمال.
- أبق `SOCIFY_IMPORT_INLINE_EXECUTION=0` في الإنتاج.

```bash
python -m scripts.run_import_worker --lease-seconds 120
python -m scripts.run_autopsy_worker
```

- لكل عامل طرفية أو مشرف خدمة مستقل؛ الأوامر مستمرة.
- عامل الاستيراد يستأنف من نقطة محفوظة ذرية كل 100 سجل.
- إجراءات القضية تحفظ حالة كل خطوة مع أثرها، وتستعيد الحجوزات المنتهية؛ الفشل القابل للإعادة ينتظر مهلة متزايدة.
- طلب الإلغاء محفوظ ويُفحص قبل الأثر التالي.
- حالة `queued` تعني انتظار المعالجة، وليست نتيجة تحليل.

## صحة الخدمة

| المسار | ما يفحصه |
|---|---|
| `/health/live` | حياة عملية التطبيق ورقم إصداره (`version`) |
| `/health/ready` | اتصال القاعدة ومخططها |
| `/api/health` | بعد المصادقة: الطوابير وإخفاقات القواعد وحالة التشغيل، وعمر نبض كل عامل وحالته وهل هو سليم (`workers`) |
| `/health/metrics` | مقاييس Prometheus: أعداد مهام الاستيراد والتحليل حسب الحالة، وعمر أقدم مهمة منتظرة، والحجوزات المنتهية، والجلسات النشطة، وحجم القاعدة، ورقم الترحيل، وعمر نبض كل عامل `socify_worker_heartbeat_age_seconds{worker="…"}`، وعمر آخر نسخة احتياطية ناجحة `socify_backup_last_success_age_seconds` بعد أول نسخة. غير موجود (404) ما لم يُضبط `SOCIFY_METRICS_TOKEN`، وبعدها يطلب `Authorization: Bearer <الرمز>` ويرد 401 بدونه. NGINX يرفضه بـ404 أيضًا؛ اجمعه من الشبكة الداخلية على `socify:5000/health/metrics`، وأضف اسم المضيف الذي يستخدمه الجامع (مثل `socify`) إلى `SOCIFY_TRUSTED_HOSTS` وإلا رُفض الطلب بـ400. لا يحوي قيمًا من القضايا أو المستخدمين أو الملفات. |

مثال إعداد Prometheus على الشبكة الداخلية، مع حفظ الرمز في ملف يقرؤه الجامع وحده:

```yaml
scrape_configs:
  - job_name: socify
    metrics_path: /health/metrics
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/socify-metrics-token
    static_configs:
      - targets: ["socify:5000"]
```

- راقب زمن الاستجابة و5xx وحجم القاعدة وWAL والأعمال الفاشلة والحجوزات المنتهية.
- يسجل التطبيق سطرًا لكل طلب API وصفحة: الطريقة والمسار والحالة والمدة ومعرّف الارتباط والمستخدم، دون نص الاستعلام أو جسم الطلب. مثال: `request method=GET path=/api/cases status=200 duration_ms=12.4 correlation_id=… user_id=3`.
- سجل الوصول الخاص بـGunicorn معطّل حتى لا تُسجَّل نصوص الاستعلام؛ اقرأ أسطر `request` بدلًا منه. طلبات `/health/*` والملفات الثابتة لا تُسجَّل، والطلب المرفوض لغياب رمز الحماية يظهر بسطر `csrf_rejected reason=… correlation_id=…`.
- يكتب كل عامل سطرًا واحدًا عند انتهاء كل مهمة في السجل `socify.workers`: `import_job_finished` أو `import_job_failed` (المعرف والقضية والحالة وعدد المقبول والمرفوض أو نوع الخطأ والمدة)، و`autopsy_job_finished` (النوع والحالة ورمز الخطأ والمحاولة والمدة). لا تدخل السطر أسماء الملفات المرفوعة ولا محتوى الأدلة ولا نص الاستثناءات؛ التفاصيل القابلة للمراجعة تبقى في سجل المهمة داخل المنصة.
- تُحذف تلقائيًا محاولات الدخول الأقدم من 7 أيام، والجلسات المنتهية أو الملغاة منذ 30 يومًا. سجل التدقيق والأدلة لا تُحذف آليًا.
- نجاح readiness لا يثبت اكتمال كل خدمة؛ تحقق من العمال وخدمة التحليل أيضًا. يكتب كل عامل نبضًا في `worker_heartbeats` عند بدئه وبعد كل مهمة وكل 30 ثانية أثناء الانتظار؛ العامل المشغول بمهمة طويلة يُعد سليمًا ما دام يحمل حجزًا ساريًا عليها. خدمة التحليل تعالج طلبًا واحدًا في كل مرة، فقد ينتظر فحص `ping` خلف تحليل طويل ويفشل مرة دون أن تكون الخدمة معطلة.
- استخدم `X-Correlation-ID` لربط الطلب بسجلاته دون نسخ محتوى الأدلة أو الأسرار.

```bash
docker compose ps
docker compose logs --tail 100 analysis autopsy-worker import-worker
```

## النسخ الاحتياطي

### النسخ المجدول في Compose

- خدمة `backup` تأخذ نسخة كل `SOCIFY_BACKUP_INTERVAL_HOURS` (الافتراضي 24 ساعة) بأداة SQLite Online Backup، وتفحص سلامتها والمفاتيح الخارجية، وتحفظها في حجم `socify-backups` باسم `socify-YYYYMMDDTHHMMSSZ.db`، أو `.db.enc` حين يُضبط `SOCIFY_BACKUP_KEY`. أول نسخة تُؤخذ عند تشغيل الخدمة إن لم توجد نسخة ناجحة خلال الفاصل.
- تبقى أحدث `SOCIFY_BACKUP_KEEP` نسخة (الافتراضي 14) وتُحذف الأقدم؛ لا تمس الخدمة ملفات أخرى في المجلد.
- كل تشغيل يُسجَّل في جدول `backup_runs` بوقته ونتيجته واسم الملف وحجمه وبصمته SHA-256، أو نوع الخطأ عند الفشل. الفشل لا يوقف الخدمة: تنتظر فاصلًا كاملًا ثم تحاول من جديد. عمر آخر نسخة ناجحة في `/health/metrics`.
- التشفير اختياري: اضبط `SOCIFY_BACKUP_KEY` في `.env` بقيمة عشوائية من 32 محرفًا على الأقل، واحفظها في مدير الأسرار منفصلة عن `SOCIFY_CREDENTIAL_KEY`. الصيغة AES-256-GCM على أجزاء من 4 MiB، لكل جزء رقم ترتيبه وعلامة الجزء الأخير، فيُكشف أي تعديل أو حذف أو تبديل ترتيب. أثناء التشغيل تُكتب نسخة غير مشفرة مؤقتة في الحجم نفسه ثم تُحذف بعد التشفير.
- النسخة تحمل أسرار القضايا مشفرة بمفتاح الاعتماد كما هي في القاعدة؛ فتحها بعد الاستعادة يحتاج `SOCIFY_CREDENTIAL_KEY` نفسه.
- انسخ الملفات خارج المضيف بانتظام؛ حجم على المضيف نفسه لا يحمي من فقده:

```bash
docker run --rm -v socifyproject_socify-backups:/backups:ro -v "$PWD/offsite:/out" alpine cp -a /backups/. /out/
```

- اسم الحجم يبدأ باسم مشروع Compose (اسم المجلد افتراضيًا)؛ اعرضه بـ`docker volume ls`.
- لأخذ نسخة فورية دون انتظار الجدول:

```bash
docker compose exec backup python -m scripts.backup_scheduler --once
```

### النسخ اليدوي

- حدّد القاعدة الفعلية أولًا. الأمثلة أدناه تفترض `instance/socify.db`.
- أوقف الكتابة أو ضع الخدمة في صيانة إذا احتجت نقطة استعادة متسقة مع بقية الملفات.
- أنشئ نسخة باسم جديد؛ أداة النسخ تستخدم SQLite Online Backup وتفحص سلامة القاعدة والمفاتيح الخارجية.

```bash
python -m scripts.backup backups/socify-backup.db --source instance/socify.db
python -m scripts.migrate --database instance/socify.db --dry-run
```

- احفظ نسخة محمية من مفاتيح التشغيل خارج القاعدة؛ النسخ لا ينقل المفاتيح تلقائيًا.
- شفّر النسخة وحدد صلاحياتها، وسجل تاريخها ومسار القاعدة ومرجع التطبيق المتوافق معها.
- في Compose، تنفذ الأداة داخل الخدمة حيث المسار `/data/socify.db`:

```bash
docker compose exec socify python -m scripts.backup /data/backups/socify-backup.db --source /data/socify.db
```

- انقل النسخة إلى تخزين احتياطي محمي مستقل؛ بقاؤها في حجم البيانات نفسه لا يحميها من فقد الحجم.

## الاستعادة

1. أوقف التطبيق وجميع العمال.
2. استعد إلى مسار جديد فارغ، مع المفاتيح الأصلية المتوافقة. احتفظ بالقاعدة القديمة.
3. افحص النسخة وطبّق الترحيل على المسار الجديد:

```bash
python -m scripts.restore backups/socify-backup.db instance/socify-restored.db --confirm RESTORE
python -m scripts.migrate --database instance/socify-restored.db
```

   - للنسخة المشفرة أضف `--decrypt`، ويُقرأ المفتاح من `SOCIFY_BACKUP_KEY`. تُفك النسخة في مجلد مؤقت بجانب الوجهة، وتُفحص وتُستعاد، ثم يُحذف الملف المؤقت. مفتاح آخر أو ملف معدّل يُرفض قبل كتابة الوجهة:

```bash
SOCIFY_BACKUP_KEY=... python -m scripts.restore backups/socify-20261126T020000Z.db.enc instance/socify-restored.db --confirm RESTORE --decrypt
```

4. اضبط `SOCIFY_DATABASE` للمسار الجديد في التطبيق والعمال.
5. تحقق من readiness والحسابات وأعداد القضايا والأدلة، وافتح دليلًا مشفرًا وتقريرًا محفوظًا قبل إعادة التوجيه.
6. اختبر الاستعادة دوريًا في بيئة منفصلة: خذ أحدث ملف من `socify-backups`، واستعده بالمفتاحين المحفوظين في مدير الأسرار، وافتح قضية ودليلًا وتقريرًا. التمرين يثبت أن الملف والمفتاحين معًا يكفيان.

## تحديث التطبيق والكتالوج

- خذ نسخة احتياطية، وحدد commit أو صورة التشغيل الحالية، واختبر الترحيل قبل تبديل الخدمة.
- للرجوع، استخدم التطبيق وقاعدة متوافقة؛ الترحيلات تراكمية وقد تحتاج استعادة النسخة السابقة.
- ترحيلات المخطط مرقّمة، ورقم آخر ترحيل طُبّق محفوظ في القاعدة نفسها، ويظهر في `python -m scripts.migrate --dry-run` باسم `migration_version`.
- كل إقلاع يطبق الترحيلات الناقصة داخل معاملة كتابة واحدة؛ إن فشل أحدها لا يتغير المخطط ولا الرقم ويتوقف الإقلاع. العمليات التي تقلع معًا تنتظر الأولى ولا تُرحّل مرتين.
- إذا كان رقم القاعدة أكبر مما يعرفه التطبيق (تشغيل إصدار أقدم على قاعدة رقّاها إصدار أحدث) يرفض التطبيق والعمال الإقلاع برسالة `Database schema version N is newer than this SOCify release supports (M)` بدل العمل على مخطط لا يعرفه. الحل: شغّل الإصدار الأحدث، أو استعد النسخة الاحتياطية المأخوذة قبل الترقية مع الإصدار الأقدم.
- لتحديث ATT&CK، استورد ملف Enterprise STIX محليًا باسم كتالوج يطابق مصدره. مثال:

```bash
python -m scripts.load_attack_snapshot enterprise-attack.json --version 20.1 --database instance/socify.db
python -m scripts.load_attack_snapshot --activate-version 20.0 --database instance/socify.db
```

- هذه الأرقام تخص كتالوج MITRE. استخدم الرقم الصحيح للملف لديك، وتحقق من الكتالوج المفعّل في الحقل `attack_version` من `GET /api/health`.
- تُحفظ بصمة الحزمة، ولا يُعاد استخدام اسم كتالوج محفوظ لمحتوى مختلف.
- حزم YARA وSigma واستخبارات التهديدات محلية؛ وثّق المصدر والترخيص ونتيجة الفحص قبل تفعيلها.

## عزل التحليل وحدود البيانات

- مقبس التحليل بصلاحية `0660`؛ طابق هوية المستخدم والمجموعة بين العميل والخدمة.
- حجم IPC لدى العميل للقراءة فقط؛ اتصال UNIX socket لا يحتاج تحويل الحجم إلى قابل للكتابة.
- يعيد العميل محاولة الاتصال فقط عند غياب المقبس أو رفضه؛ لا يعيد إرسال طلب وصل إلى الخدمة.
- عند تعذر العزل، أصلح الخدمة بدل نقل التحليل إلى عملية غير معزولة.
- البريد: حد 2 MiB، عمق MIME حتى 5، و100 جزء و200 رأس و25 مرفقًا.
- تصدير السجلات: حتى 100000 سجل للطلب. البيانات الوصفية المحجوبة لا تعادل تحقيقًا كاملًا؛ تنزيل الأصل يحتاج صلاحية مستقلة.
- PCAP/PCAPNG: بيانات وصفية دون التقاط حي أو فك TLS أو إعادة تجميع TCP؛ بعض DNS وSNI المجزأ أو المشفر قد لا يُستخرج.
- SQLite: استخدم تخزينًا محليًا متوافقًا مع WAL، وراقب التنافس بين العمال. لا تنسخ ملف قاعدة مفتوحة وحده كبديل عن أداة النسخ.

## شهادة بناء مؤسسية

- يدعم Dockerfile سر بناء اختياريًا `build_ca` لشهادة الثقة العامة فقط.
- لا تمرر مفتاحًا خاصًا أو بيانات proxy إلى الصورة، ولا تعطل TLS:

```bash
docker build --secret id=build_ca,src=/path/to/trusted-ca-bundle.pem --target runtime .
```

## تدوير مفتاح التشفير

يحمي `SOCIFY_CREDENTIAL_KEY` أسرار MFA وبيانات اعتماد المصادر ومحتوى الأدلة والعينات والتقارير والكبسولات. التدوير يغيّر المفتاح الذي يحمي هذه القيم ولا يغيّر محتواها ولا بصماتها.

1. خذ نسخة احتياطية من القاعدة واحتفظ بالمفتاح الحالي معها.
2. اضبط `SOCIFY_CREDENTIAL_KEY` على المفتاح الجديد و`SOCIFY_CREDENTIAL_KEY_PREVIOUS` على المفتاح الحالي، ثم أعد تشغيل كل الخدمات. من هذه اللحظة يُكتب كل جديد بالمفتاح الجديد ويُقرأ القديم بالمفتاح السابق.
3. شغّل `python -m scripts.rotate_credential_key` لمعرفة عدد القيم التي ما زالت تحت المفتاح السابق، ثم `python -m scripts.rotate_credential_key --apply` لإعادة تشفيرها. في Compose: `docker compose exec socify python -m scripts.rotate_credential_key --apply`.
4. عندما يطبع الأمر `"previous_key_still_needed": false` احذف `SOCIFY_CREDENTIAL_KEY_PREVIOUS` وأعد التشغيل، ثم جرّب فتح دليل وتنزيل تقرير.

- إعادة التشفير تتم في معاملة واحدة: إن تعذر فك قيمة واحدة بأيٍّ من المفتاحين يتوقف الأمر دون تغيير أي شيء، ويذكر الجدول ورقم الصف.
- جداول الأدلة والعينات والتقارير والكبسولات تمنع التعديل بمحفزات في القاعدة. يرفع الأمر هذه المحفزات داخل معاملته فقط ويعيدها قبل الحفظ، ويتحقق من أن المحتوى بعد إعادة التشفير يطابق ما قبله.
- النسخ الاحتياطية المأخوذة قبل التدوير تحتاج المفتاح السابق؛ احتفظ به ما دامت تلك النسخ محفوظة.
