# برومت تنفيذ SOCify V4 — مواصفات التنفيذ والقبول

## الهدف والمرجع
طوّر المستودع https://github.com/7zy4/SOCifyProject انطلاقًا من آخر رأس للفرع `socify-version-3`، وهو عند بدء العمل `7851d3b329ea4aecdff5a3077cd914a22055a34b`. أنشئ فرعًا مستقلًا اسمه `V4` دون تعديل V3 أو إعادة كتابة تاريخه. احفظ هذا البرومت قبل تعديل المنطق. الناتج تطبيق قابل للتشغيل، مع دليل التجربة والحسابات وتقرير تحقق صريح، وليس نموذج واجهة فقط.

## المرحلة 1: الجرد والحماية من التراجع
1. افحص Flask وSQLite وواجهات JavaScript الحالية وOpenAPI ومسارات التوافق. لا تستبدل المنصة بقالب جديد.
2. احتفظ بالمراقبة بقنواتها وترقيمها، استيراد السجلات وبحثها وتصديرها، الأصول، المؤشرات والإثراء المحلي، EML، العينات وYARA وSigma، الخط الزمني والرسم والتحقيق و5 Whys، الاستجابة والتصعيد وSLA وتسليم المناوبة، المهام والفريق، الحيازة والتقارير والاعتماد والكبسولات والمصادقة والجلسات وMFA واللغتين والثيمين.
3. شغّل الاختبارات الحالية ثم اختبارات V4 الخاصة بالسياسة الجديدة. اختبارات التوافق القديمة يمكن أن تعطل السياسة صراحة في إعدادات الاختبار؛ يجب أن تغطي اختبارات مستقلة إعدادات التشغيل الافتراضية الفعلية.

## المرحلة 2: القضايا والاعتماد ونطاق التحقيق
1. يبدأ المستخدم بعد الدخول من `/cases`: القضايا المصرح له بها، حالتها، المسؤول والاعتماد، إنشاء طلب قضية، اختيار نطاق عمل. المحلل يرى قضاياه وعضوياته فقط؛ المدير يدير قضايا مساحة عمله.
2. كل قضية جديدة تبدأ `pending` لاعتماد المدير، بما في ذلك ما ينشئه المدير. اعرض اسم الطلب وسببه وهدفه فقط قبل الاعتماد. امنع أعمال التحقيق والرفع والتحليل والتقارير والانتقالات على الخادم قبل الاعتماد؛ لا يكفي إخفاء الأزرار.
3. أضف سجل اعتماد منفصلًا بحالة pending/approved/rejected، المراجع والتاريخ وسبب القرار وإصدار للتزامن. المدير أو مسؤول المنصة بصلاحية مناسبة وحدهما يقرران. التكرار أو الإصدار القديم يرجع تعارضًا ولا ينشئ قرارين. يبقى الطلب المرفوض مقفولًا ومتاحًا للمراجعة.
4. ترحيل قضايا V3 القائمة يحافظ على وصولها ويعلّمها كمعتمدة موروثة مع مصدر واضح؛ لا تعطل تاريخ المستخدمين. لا تزرع بيانات تجريبية داخل قاعدة قائمة.
5. يختار المستخدم قضية معتمدة واحدة أو قضيتين معتمدتين مرتبطتين صراحة. المدير ينشئ العلاقة بسبب موثق؛ رفض قضية ثالثة، علاقة ذاتية، علاقة غير موجودة، مساحة عمل أخرى أو قضية غير مرئية. خزّن الاختيار في جلسة الخادم.
6. في النطاق المزدوج اعرض القضيتين بوضوح مع تبديل القضية النشطة. كل عملية كتابة تتجه إلى قضية واحدة ظاهرة، ولا تخلط الأدلة أو التقارير تلقائيًا. المراقبة تجمع النطاق المختار فقط، وأدوات التفاصيل تعمل على القضية النشطة فقط.
7. أعد التحقق من العضوية والاعتماد والعلاقة وصلاحيات دفعات الاستيراد في كل طلب. عند سحب الوصول أو تغيير الحساب امسح الاختيار أو ارفضه؛ لا تعتمد على localStorage أو معاملات URL للتفويض. امنع تسريب الأعداد والبحث والتصدير والتفاصيل والروابط المتداخلة من خارج النطاق.

## المرحلة 3: تجربة الاستخدام والتنقل
1. حافظ على تنظيم SOC المألوف: مراقبة، سجلات، أصول، استخبارات، بريد، تحليل، تقارير، ثم أدوات الفريق والإدارة.
2. استخدم الشريط الجانبي للمقاصد الرئيسية وحده؛ أزل شريط المقاصد العلوي المكرر. اجعل الأعلى للهوية ونطاق العمل والمظهر واللغة والحساب. تجنب نسخ تبويبات السجلات والتقارير في موضعين؛ أبقِ تبويبات التحقيق التي تضيف سياقًا مستقلًا.
3. اجعل اختيار القضية مسارًا واضحًا في البداية مع حالات فارغة وانتظار ورفض وصلاحية ناقصة. لا تعرض صفحة أدوات فارغة دون شرح وخطوة تالية.
4. أضف أيقونة تبديل الحسابات: في بيئة التجربة المعزولة تسمح بالانتقال إلى حسابات الفريق المزروعة فقط عبر جلسة تسجيل دخول حقيقية جديدة مسجلة بالتدقيق، مع تدوير الجلسة ومسح النطاق. في التشغيل العادي انتقل إلى تسجيل الدخول ولا توفر انتحالًا.
5. حافظ على لوحة المفاتيح وترتيب التركيز وEscape للنوافذ وaria labels والإعلانات وأهداف لمس 44px تقريبًا. دعم RTL/LTR، معرفات وعناوين IP وhash داخل bdi، وعدم ترجمة الأدلة. اختبر 390px و1440px وثيمين ولغتين وعدم وجود overflow عام.

## المرحلة 4: الهوية البصرية
استخلص لغة رسوم التحقيق المصورة الداكنة: فحم وحبر وكحلي بارد وأصفر إشارة وورق عاجي، حواف واضحة وظلال مطبوعة قصيرة وتكتشر halftone منخفض التباين في التنقل ومساحات العناوين فقط. لا تستخدم اسم Batman أو شعاراته أو رسوماته أو شخصياته أو نصوصًا تشير إليه داخل المنتج. لا تشتر أو تنسخ أصول الآخرين.

- الداكن: خلفية #0C1017، لوحة #151C27، نص #F4F0E5، نص ثانوي #BCC4D0، أصفر #F4CE46 ونص زر #10141C.
- الفاتح: ورق #F5F0E4، لوحة #FFFCF4، نص #172131، نص ثانوي #4D5969، حبر كحلي وحدود واضحة، زر أصفر بنص غامق.
- خط عربي محلي Almarai وإنجليزي IBM Plex Sans، عناوين ثقيلة دون إمالة النصوص العربية. لا تضع texture خلف السجلات أو الشيفرات أو النماذج. التباين WCAG AA للنصوص 4.5:1 وللعناصر 3:1، التركيز واضح، reduced-motion محترم.
- حدّث مصدر design-tokens وCSS معًا. أبقِ ثيمًا فاتحًا وداكنًا؛ ابدأ التجربة بالداكن إذا لم يختر المستخدم غيره. التقارير المطبوعة تبقى وثائق مقروءة.
- مراجع استلهام فقط: https://dribbble.com/shots/26289631-The-Batman-Comic-website وhttps://github.com/tatrong/batpanel-dashboard وhttps://kaboom-ui-kit.pages.dev/ . لا تضف اعتمادية لمجرد محاكاة المظهر.

## المرحلة 5: فريق وبيانات تجربة صغيرة ومترابطة
1. أنشئ أمر تهيئة صريحًا يستهدف قاعدة جديدة منفصلة فقط، يرفض الإنتاج وقاعدة موجودة. لا توجد كلمة مرور ثابتة بالكود ولا وضع تجريبي تلقائي في الإنتاج. ولّد كلمات مرور قوية مختلفة واحفظها في تسليم خاص خارج Git.
2. فريق من أربعة: مدير، محلل L1، مستجيب L2، مراجع قراءة واعتماد تقارير بحسب الصلاحيات الأصلية. وثّق الصلاحيات الفعلية والحدود لكل حساب.
3. قضية أساسية: تصيد فاتورة أدى لاتصال خارجي مشتبه؛ بريد EML آمن، سجل بوابة بريد وDNS وproxy وendpoint وauth، أصول مع owner/OS/importance، مؤشرات URL/IP/domain/hash، تنبيهات وقرارات، مهام، فرضيات وخط زمني وسبب جذري واستجابة وتصحيح وتصعيد وكتيب وSLA وملاحظات وحيازة.
4. قضية ثانية صغيرة مرتبطة لاختبار المقارنة؛ طلب ثالث معلق لاعتماد المدير؛ قضية رابعة غير مرتبطة وغير مسندة للمحلل لاختبار العزل. اجعل القضايا الإضافية محدودة لا بيانات ضخمة.
5. استخدم نطاقات `.test` و`.invalid` وIP توثيقية فقط، بيانات أشخاص مختلقة، أوقات UTC متسقة، وأصول عينات غير قابلة للتنفيذ. وفّر ملفات CSV/JSON/EML وعينة نصية آمنة للتجربة.
6. مرر البيانات عبر APIs ومسارات التشفير والحيازة والتحقق الفعلية حيث أمكن. لا تكتب تقارير تحليل مزيفة تدعي تشغيل خدمة لم تعمل. أدرج مصدر الإثراء المحلي ونوعه التجريبي وتاريخه وانتهاءه.
7. وفّر خطوات تجربة لكل ميزة مع نتيجة متوقعة وحالات إيجابية وسلبية. لا تتصل فعليًا بعناوين الشك ولا تفتح الروابط آليًا.

## المرحلة 6: الأمن والتشغيل والتحقق
1. أبقِ bcrypt وتشفير الأدلة وCSRF وCSP وHttpOnly وSameSite وتحديد المعدل وtrusted hosts وضوابط الاحتفاظ وتفويض API. افحص IDOR عبر مسارات cases/incidents والمعرفات الفرعية، منع SQL injection وXSS وCSV formula injection، وحدود الملفات/المحتوى والأنواع والأعداد.
2. التحليل البسيط ساكن ومعزول بلا شبكة؛ لا تدّعِ detonation ديناميكي. شغّل خدمة التحليل الحالية في Docker بقيود المشروع واختبر SHA256/YARA واستخراج النصوص والروابط. فشل الخدمة يظهر كفشل صريح مع إعادة محاولة، وليس نجاحًا فارغًا.
3. افحص بحث IP وURL داخل السجلات للمختار فقط، الإثراء المحلي، Sigma، EML دون HTML نشط، إنشاء التقرير الفوري والصيغ الخمس والمراجعة، الحيازة والتصدير والكبسولة، وعامل المهام الخلفي. لا يشتغل العامل على قضية غير معتمدة أو مستخدم سُحب وصوله.
4. شغّل pytest للتكامل والأمن والوحدات، ثم اختبارات Playwright ذات صلة مع axe، وتحليل Python وJavaScript وأدوات الأمن المتاحة. وثّق النتائج بالأعداد الدقيقة والأوامر وأي تعذر بيئي، ولا تصف ميزة غير مختبرة بأنها اجتازت.
5. سجل كل عيب UX/أمني/تشغيلي قابل لإعادة الإنتاج، سببه وإصلاحه ودليل إعادة الاختبار. أعد الاختبارات بعد الإصلاحات، وتجنب إعادة فحوص واسعة دون تغيير يبررها.
6. سلّم البرومت، دليل تشغيل V4، دليل الحسابات الخاص، مصفوفة الميزات والاختبارات، تقرير المراجعة، وفرع V4 على GitHub. لا تنشر قاعدة البيانات أو كلمات المرور أو مفاتيح الجلسة أو الأدلة الخاصة في Git. لا تدمج V4 في V3 أو main.
